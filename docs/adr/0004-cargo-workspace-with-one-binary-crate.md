# A Cargo workspace with one binary crate

We are building Holosmith as a Rust binary. The repo holds a Cargo **workspace** at its root with a single member, the binary crate `crates/holosmith`, and the workspace root owns the things every future crate must share: `[workspace.package]` (version, edition, `rust-version`), `[workspace.dependencies]`, one release profile, one lints table, and the committed `Cargo.lock`. Everything else has a fixed home from day one: `pins/` for pinned external versions, `web/` for the Vite app whose `web/dist` output is embedded into the binary, `scripts/` for the build and check scripts, `dist/<target-triple>/holosmith` for built artifacts, `docs/build.md` for how to build.

Reasons: 79 stories follow this one, and roughly half of them end with "and then the server, the proxies, the container helpers and the CLI have to agree". A single crate at the repo root is simpler for exactly one story and then forces a decision later, at the point where moving `src/` into `crates/` rewrites every path, every `cargo` invocation in `scripts/`, and every doc that says where a file lives. The workspace costs one extra file now and buys a stable place for the second crate (`crates/holosmith-web` for the embedded app, or extracting the DB layer) without moving the binary. The rejected alternative is the ordinary one, which is why this is written down: readers of a one-binary repo will assume the crate is at the root and wonder why it is not.

Consequence we accept: `cargo run` from the repo root needs `-p holosmith`, and every path below the root is one level deeper than someone guessing would expect. The frontend is deliberately **not** a crate and not a workspace member: `web/` is a Vite project built by `npm`, and its output is embedded with `include_bytes!`/`include_dir!`, so it must not appear in `Cargo.toml`.
