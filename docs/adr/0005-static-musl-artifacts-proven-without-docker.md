# Only statically linked musl artifacts, proven without Docker

The only artifacts we ship are `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` release builds, and both must be plain `ET_EXEC` static binaries, not static PIE: the two musl targets carry `rustflags = ["-C", "relocation-model=static"]` in `.cargo/config.toml`, so `file` reports `statically linked` for both and `readelf -d` prints "There is no dynamic section in this file". SQLite is compiled from source with the `bundled` feature for the same targets, so the C toolchain crosses as well.

Why non-PIE: the default for `x86_64-unknown-linux-musl` is `static-pie linked`, which is equally static at run time but does not satisfy the spec's stated check (`file` reports statically linked) without an explanation every reader has to reconstruct. The trade is real and worth recording: we give up address-space randomisation for the main binary in exchange for an artifact whose `file` output is self-evidently what the spec promised, and a deployment check that cannot be misread.

Why verify locally rather than only in a release: the machine this is built on had no Docker daemon when this was written, so "runs in an empty container" would otherwise be an unproven claim held by hope until. `scripts/check-static.sh` replaces it with two stronger checks, and neither fetches anything: the artifact runs in a `FROM scratch` image holding it and nothing else — no `/lib`, no `/usr`, no shell, no loader — and the aarch64 artifact runs under `qemu-aarch64-static` when that optional dev tool is on `PATH`, printing a single loud `SKIP` line when it is not. The staticness this ADR is about is still proved without Docker at all — `file` and `readelf` need nothing — and the empty root is the one part of the check that now wants a daemon: the image is built per target on the operator's daemon and removed once its check has run. ADR-0108 records why the sandbox that used to stand in for it could not outlive the gate moving into a container, and what the daemon requirement costs. Neither check may fail the build because of a missing tool, and no repo script downloads anything: the emulator is a machine-local prerequisite, documented in `AGENTS.md`, not a declared dependency.

What this does and does not prove: it proves the artifact has no dynamic loader and no userspace dependency, on both architectures, and — for the host's architecture — that a real container runtime starts it from a filesystem holding nothing but itself. It does not prove the same on an aarch64 *host* (this host measures that arm through the emulator, which is the filesystem the artifact ran in, not an aarch64 kernel) or anything about a deployment's own runtime; that is the smoke run and the deploy in phase 2, and it stays an open acceptance item until then rather than being quietly claimed here.

Consequence we accept: nothing in the repo may export `RUSTFLAGS`, because cargo silently ignores `target.*.rustflags` from config when that variable is set — the build would produce static-PIE again with no error. `check-static.sh` therefore asserts the property on the produced artifacts, so a future `RUSTFLAGS` mistake fails loudly instead of shipping a differently linked binary.
