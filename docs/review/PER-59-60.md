## P2 — should fix

**P2-1 (Standards) · `docker::absolute` is dead, its name and doc are false, and its test cannot fail.**
`crates/holosmith/src/docker.rs:173-186` — the function is called from nowhere (`grep 'absolute('` finds only its own test); it does not absolutise anything (`path.to_str()`), and its doc claims "The absolute form of a path … Every path in a run argument therefore goes through here", which is false: `Mount::argument` (`container.rs:112-120`) uses `Path::display()`, i.e. the lossy conversion the doc says this prevents. The test at `docker.rs:239-245` is named `a_path_that_is_not_utf8_is_refused_rather_than_lossily_converted` and asserts only the happy path of a UTF-8 literal.
*Smallest fix:* delete `absolute` and its test. If the UTF-8 concern is real, it belongs in `Mount::argument` (there is a precedent for refusing it: `worktree.rs` paths are `String`-typed).

**P2-2 (Standards) · "A failure to remove is logged" is not logged.**
`crates/holosmith/src/backend/docker.rs:214-219` promises "a container the daemon cannot remove is a machine problem the log names", but `:220-241` only matches `Ok(false)` and drops `Err(_)` (spawn failure, `JoinError`, docker missing) on the floor; `remove_network` (`:236-243`) is `let _ = …`, so a wedged daemon and a clean "not found" are indistinguishable. This is the class the gate deliberately guards elsewhere (`verify.sh:2053-2065`: "a `warn` nothing greps is a `warn` that can be deleted").
*Smallest fix:* `match removed { Ok(true) => {}, Ok(false) => debug!("there was no container to remove"), Err(error) => warn!(%error, "the container could not be removed") }`, and the same one-armed match in `remove_network`.

**P2-3 (Standards) · The four new config keys are outside `every_documented_key_is_read_into_its_field`, and `EVERY_KEY`'s doc comment is now false.**
`crates/holosmith/src/config/mod.rs:921` says "One file that sets **every documented key** to a value that is not the default"; `agent_image`, `container_cpus`, `container_memory_mb`, `container_pids` are absent from it and from the assertions at `:993-1032`. `schema.rs:721-753` proves only *shape* agreement, so e.g. `set_container_pids` writing `config.container_memory_mb` would keep the whole suite green. ADR-0006's documented recipe for a key ends "and a test", and `mod.rs:471` names this test as where the misdirected-setter guarantee lives.
*Smallest fix:* four lines in `EVERY_KEY` and four `assert_eq!`s.

**P2-4 (Spec/Standards) · ADR-0036 and `docs/build.md` claim "each refuses `0`"; no test can fail if that refusal is deleted.**
`docs/adr/0036-hs-028-fills-the-network-step.md:41-45`, `docs/build.md:367-371` ("all three refuse it"), `schema.rs:544-556` (`positive`). Nothing in the tree runs `container_cpus = 0`, `container_memory_mb = 0`, `container_pids = 0` or `agent_image = ""` through `validate_text`. Grep for the four key names outside `src/`+`schema.rs` finds only `verify.sh:465` (all nonzero) and the golden.
*Smallest fix:* three `assert_eq!(problems_of("container_cpus = 0\n"), …)` beside `history_window_must_be_at_least_one` (`mod.rs:1156`), plus one for the empty image.

**P2-5 (Spec) · Two V1 clauses can pass because the command is missing, not because the kernel refused.**
`crates/holosmith/tests/container.rs:227-228` runs `mount -o remount,rw /` and `umount /work` with `2>&1` thrown away, and `:378-380` asserts only `!= "0"` — exit **127** ("not found") satisfies that. The same hole is in `scripts/verify.sh:396-400`. Adjacent: `verify.sh:428-430` reads `id -u` as "the first line of stdout" and passes if `id` is absent (the first line would then be `hooks_write=…`, also `!= 0`), so "the process is not root" is vacuous without coreutils.
*Smallest fix:* in the probe, print `command -v mount >/dev/null; echo mount_present=$?` and assert **0**, or assert the refused codes are non-zero **and not 127**; for the uid, `id -u 2>/dev/null || echo missing` and require a number.

**P2-6 (Standards) · `provision`'s summary doc line still describes a function that no longer exists.**
`crates/holosmith/src/backend/docker.rs:246-247`: "Run a step that has no implementation yet: one sentence per step, and the sentence names the story that fills it" — three of the four arms now implement (`:253-260`). The paragraph below it was updated; the summary was not.
*Smallest fix:* "Run the step: three are real from HS-025/HS-028, and the agent step refuses in one sentence naming HS-031."

**P2-7 (Spec) · Unrequested scope: the development sandbox is given the host Docker socket.**
`bwrap.sh:70-84` (`DOCKER=()` … `--bind "$sock" /var/run/docker.sock`) and `:109`. Neither story asks for it; it is in neither plan's "shape"/"docs" list and in no ADR, and `docs/build.md`'s prerequisites say nothing about it. It is root-equivalent for anything inside the sandbox — which is where every future agent session in this repo runs. The comment at `:70-76` argues the grant deliberately and correctly, and the point ("anything that can reach the socket can start a container with `/` mounted") is the reason it deserves a line in the story's deliverable.
*Smallest fix:* one sentence in `docs/build.md`'s prerequisites ("the dev sandbox binds the daemon socket; a machine without one gets no `DOCKER` binds") so the grant is discoverable by the next reader who asks why a reviewing agent can create containers.

## P3 — nits

- **`docs/build.md:193-201` was appended, not reflowed.** The line ending "…— V1, see ADR-0035), and the container (`case_docker_container`, which boots a Docker run over a real" is ~135 columns against ~100 everywhere around it, which breaches the repo's own rule (`RESUME.md:890-891`: "its prose must be **reflowed** (~100 columns), not just appended to").
- **The config golden now pins the crate version.** `config/mod.rs:239` (`format!("agent-image:{}", env!("CARGO_PKG_VERSION"))`) plus `tests/golden/config-default.toml:11` (`agent-image:0.1.0`) means **every version bump** turns `render.rs:133-138` and `tests/config_cli.rs:220,236` red. `RESUME.md:888-889` only warns about *new keys*. Either accept and add one sentence to that rule, or note it in ADR-0035.
- **Two homes for one default.** `container.rs:252-262` (`Limits::default()` = 2/4096/512) repeats `config/mod.rs:240-242`, and `ContainerSettings::at` (`container.rs:281-288`) takes the image from `Config::default()` but the limits from `Limits::default()` — so the "one place that knows where … the limits come from" claim in `:262-267` is not quite true for the `at` constructor.
- **`Missing` is misnamed for half of what it reports.** `container.rs:216-233`: it also carries "is not a file"/"is not a directory" (wrong-kind) entries, and its `Display` prefix is "the worktree cannot be mounted: …" even when the source at fault is `.git/config`. `MountProblem`/`Unmountable` and "the mounts cannot be made: …" would say what it holds.
- **"spec item 6's resource limits" is a citation that does not resolve.** `container.rs:235,253,382` and `config/mod.rs:196` — item 6 is naming and exit handling; limits live in `HolosmithSpec.md`'s "Known and accepted risks" (last row) and the story cites "item 6, Known risks (resource limits)".
- **`RESUME.md` is now stale in two places this diff made stale.** `:597` (`DockerBackend::new(projects_root)` "provisions the worktree and refuses every other operation") and the "Not built yet" bullet's "the network, container and agent steps still refuse" (`:593-595`); `:889` still says "currently 26" (it is 31 now). The plans defer `RESUME.md` to the end of the run — record it there, not as a blocker.
- **The gate's V1 case uses a layout production never has.** `scripts/verify.sh:344,366-370` builds the worktree at `$root/project/.worktrees/$id` (inside the repository); production and `tests/container.rs` use `<projects>/.worktrees/<id>` with the repository at `<projects>/<project>`. The properties under test are unaffected, but the `-v <worktree>:/work` being proven is a path shape no session will ever have.
- **`tests/container.rs:3` — "the only place in the tree that runs a real container."** `verify.sh`'s two new cases do too; say "the only *test* that runs one".
