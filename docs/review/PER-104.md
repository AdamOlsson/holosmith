# Review — PER-104 (HS-072, `hub deploy` and `hub host` CLI)

Fixed point `50c7d34`; the story is commits `bcd57c2` and `8e46df1`. Reviewed read-only by a fresh `reviewer` child
against `git diff 50c7d34` (files added with `git add`, so new files appear in the diff). The review is verbatim;
the `## Resolution` table below it is mine.

## Review

The story is substantially what HS-072 asked for, and the design is the right one: `hub host` is a client of the routes that own the rules, `hub deploy` is `server deploy` with a `Kind`, and the union is written into the config the install boots from. Three things I would not merge as they stand: the deploy's new tail asserts on `--dry-run` a state change that did not happen, the ADR index lost ADR-0076's summary and re-attributed its text to ADR-0077, and three documents claim `case_hub_deploy` needs no `openssl` when its own arms run `openssl` twice. Everything else below is polish.

## Standards

1. **major — the new tail claims an install a `--dry-run` did not make.** `crates/holosmith/src/commands/deploy.rs:75-79` prints `deploy: role:` and the role-dependent `next:` lines after any run that reached the end, with no `args.dry_run` guard, and `role_line` (`:86`) words the change in the past tense: `deploy: role: both (this machine's config said `server`, and `hub deploy` added the hub half)`. On `hub deploy --dry-run` over a `server` config, the report above it says `deploy: dry run` and nothing was written — the file still says `server`. That is exactly the "say only what you measured" rule the five-word report exists for, and `resume()` (`:129`) already models the opposite discipline. The gate cannot catch it: the dry-run arm is hub-on-hub, where `found == role` and the parenthetical never prints (`scripts/verify.sh:5192`). Smallest fix: `if !args.dry_run` around the role line, or render it as `deploy: role: both (would be)`.

2. **major — ADR-0076's index entry lost its summary and its text moved to ADR-0077.** `docs/stories/README.md:199` is now a bare link, and the whole Computers-screen description that belonged to it now trails ADR-0077's bullet on `:200` (after "…(HS-072). — **the Computers screen reads each machine over the hop it already forwards with**: no new route, no migration…"). The index therefore attributes ADR-0076's decision to ADR-0077 and no longer describes ADR-0076 at all. The count (`:117`, "Seventy-seven") is correct — 77 bullets, ADR-0001…0077. Fix: restore `:199`'s summary and delete the appended tail from `:200`.

3. **major — "`case_hub_deploy` needs no `openssl`" is false, and the case fails rather than SKIPs without it.** Claimed at `docs/adr/0077-…md:163` ("the one case in the run that needs no daemon, no image and no `openssl`"), `docs/build.md:549-551`, and the ADR index line (`docs/stories/README.md:200`). But the case runs `hub deploy --root` for real, and (a) step 2 generates the VAPID pair by running `openssl ecparam …` whenever the file is absent (`crates/holosmith/src/deploy.rs:1317-1337`), which on a fresh `--root` tree it always is — the case asserts the product of that call (`scripts/verify.sh:5258`, `var/lib/holosmith/secrets/vapid.toml 600`); and (b) step 7 runs `doctor --full`, whose `openssl` finding is a **failure** when the program is not runnable (`crates/holosmith/src/doctor.rs:270-281`), so step 7 fails (deploy.rs:2099-2102). `deploy_machine_shims` supplies only `tailscale` (`scripts/verify.sh:9612-9685`), so on a machine without `openssl` the case dies at `$name/run/exit`, not the `SKIP` line the docs promise. Fix the sentence, or shim/SKIP it. Worth a second look on its own terms: a hub runs no push channel, so `doctor --full`'s `openssl` question is the third member of the Docker/git carve-out that `doctor.rs:209` makes for `Role::Hub` and this story did not extend.

4. **minor — a stale "two facts" claim in the function the story just widened.** `crates/holosmith/src/deploy.rs:1708` still says "the rendering is a public function of exactly two facts — where the binary is, and whether this is a privileged install", while the signature at `:1721` takes three and the paragraph added at `:1717` describes the third. One-line edit.

5. **minor — the hub's satisfied clause reads as a fact about the user, not about this run.** `crates/holosmith/src/deploy.rs:1044-1052`: on a `both` machine that ran `server deploy` first, step 2 prints "the service user holosmith **exists and joins no group**", which parses as "it is in none" — the very claim the doc above it says it is avoiding. The doc's defence (that "joins" is this run's action) does not survive the sentence's subject. Smallest fix: "exists, and this run joined it to no group".

6. **minor (Middle Man) — `run_deploy` decides nothing and says it does.** `crates/holosmith/src/commands/hub.rs:26-29` is one delegating line documented as "the deploy, told which half it installs", but the `Kind` is chosen by the caller (`crates/holosmith/src/main.rs:85-92`). Delete the wrapper and call `commands::deploy::run`, or move the `Kind` into it so the doc is true.

7. **nit — "authority" where the code sends a host.** `crates/holosmith/src/hosts/client.rs:14` and `:55` (and ADR-0077 D2) say the client sends "the origin's own **authority**" in `Host`; it sends `Origin::host()`, which is documented as "the authority *without its port*" (`crates/holosmith/src/config/mod.rs:137-143`). Harmless — `guard::host_of` strips ports anyway (`http/guard.rs:176-190`) — but the sentence describes a header the code does not write.

## Spec

Per-bullet, as written:

- **B1 (steps 1 without Docker/git, 2 without the group, 5, 6, 7; no images, no proxies) — true, and measured.** `Kind::skip` produces `Word::Skipped` for 3 and 4 with the reason (`deploy.rs:186-200`, loop at `:614-624`); the checked config carries `Kind::Hub` into `doctor` (`doctor.rs:209`), so the filter is the existing one, not a second; step 2's group is a parameter all the way to `Action::UserAdd::group: Option<String>`. Measured by `tests/deploy.rs`'s `a_hub_deploy_runs_five_steps…` (empty `builds()`/`calls()`, unit without `docker.service`) and by the gate's dry-run and `--root` arms. Printing 3 and 4 as `skipped` goes beyond "runs 1, 2, 5, 6, 7", but ADR-0056's five-word contract and the line-for-line diff against a server run make that reading defensible.
- **B2 (same checks as `POST /api/hosts`) — true by construction.** The client sends the request and the routes keep the rules; `hub_cli.rs` measures the request bytes and the envelope split, not the rules. Note that `list` performs none (a `GET`) and `remove`'s checks are the `DELETE`'s own (`http/hosts.rs:122-155`).
- **B3 (`--dry-run` works) — true**, with finding Standards-1 attached to its tail.
- **B4 (`server deploy` + `hub deploy` ⇒ `both`, API unchanged) — true.** `union` covers all six arms (`tests/deploy.rs::the_two_halves_union_into_both_and_nothing_is_refused`), the union is what step 2 renders, the unit follows the union, the gate's stub boot answers `"role":"both"` with `/api/hosts` and `/api/sessions` at 200, and `http/hosts.rs` gains only a derive.
- **B5 (`status` reports the health of every registered machine) — true as a reading, and the reading is disclosed.** See Spec-1.

1. **minor — B5's "health" is the last probe's, not a live check, and the spec's own `status` row still says "last health of registered machines".** `crates/holosmith/src/status.rs:207-238` reads the table; `hosts::facts` prints `checked <n>s ago` (`hosts/mod.rs:329-361`), which is the honesty mechanism and is why I would not block on it. What is missing is the sentence at the point of authority: ADR-0077 D6 records the refusal to fan out, `HolosmithSpec.md:350` was not touched, and a hub up for a week will report last Tuesday's `reachable` as its only CLI answer. One clause in the spec row (or a line in the story) would close it.

2. **minor — the spec's step 7 sentence and the Commands row for `hub host` were not amended to match the code.** `HolosmithSpec.md:374` says step 7 prints "`holosmith key set <provider>` and registering the machine in a hub"; a hub deploy prints neither `key set` (correctly — no key proxy) nor that wording, and a server deploy's second next step is now `on the hub: holosmith hub host add <name> <url>`. And `HolosmithSpec.md:347` spells `remove <name>` while the CLI also takes `--force` (the API's `?force=true`). Both deviations are the right calls and both are recorded in ADR-0077 — the Commands table row for `hub deploy` *was* edited in this diff (`:346`), so its neighbours should have been too.

**Non-goals respected:** no `--ssh`/`--binary`, no `upgrade`/`rollback`, no cross-machine sessions, no change to `POST /api/hosts`' rules (only `Serialize` → `Serialize, serde::Deserialize` and `pub(crate) mod`), no image or proxy work, no migration, no new config key, no new route.

**Checked and clean:** the four guards against the client's actual head (`http/guard.rs:89-129` — `Origin` compared as text against `control_origin`, `Host` reduced to a port-less name and matched against `allowed_hosts` + the implicit `localhost`/`127.0.0.1`, content type only on non-`GET`, `Content-Length: 0` on `DELETE`); `segment()` is encoding, not a second `name_problem` (`hosts/mod.rs:172-179` stays the alphabet); the read-only `db::Reader::hosts()` and the `Ok(None)` vs `Err` split, with `NO_REGISTRY` and `deploy::refusal` gone from the tree and no stale references; `Path::exists()` vs `ErrorKind::NotFound` in the new reads; `grep -qF --` on the backticked sentence and `"\nmachine "` (not `"machine "`) on the row lines; the `ItemKind` rename leaving no stragglers and `Kind as ImageKind` in the test; `unit_text`'s bytes for a server unchanged (the `{requires}` continuation still emits `Requires=docker.service\n` at column 0) and the `--root` remark paths untouched; the union being one function with three callers (`run_as`, `role_line`, and the tests); `hosts::facts` as the one row sentence for both `status` and `hub host list`; the gate's 82 assertions as written (the seeded `thisbox` row really does print `version` — `hosts/mod.rs:427-437` fills it on the local shortcut — and `attic`'s probe sentence really does contain the origin, `probe.rs:269-276`), its single `SKIP` (missing `python3`, which genuinely picks three ports) hiding nothing, and the honest exclusions ADR-0077 D7 records (no image-tag assertion, no tailnet, no unit boot). Two small things I looked at and did not file: `status::machines` duplicates `counts`' open/missing/failed shape (`status.rs:205-238` vs `:273-304`) — ~12 lines, and the second block's doc points at the first — and `client::MAX_ANSWER` truncation is reported as "something else is on that port" (`client.rs:202`, `:132`), which blames the port for this client's own cap at ~1000 rows. I executed nothing; if the openssl point needs confirming rather than reading, run `case_hub_deploy` with an `openssl`-free `PATH`.

## Resolution

Nine findings: three major, four minor, one nit, plus two spec deviations and two observations the reviewer
recorded without filing. **Every one is fixed or dismissed with a citation; none is dismissed without one.**

| # | Finding | Disposition |
| --- | --- | --- |
| S1 | **major** — the deploy's tail asserts a role change a `--dry-run` did not make, and `role_line` words it in the past tense | **Fixed.** `role_line(found, role, kind, dry_run)` renders a plan as `deploy: role: both (would be: this machine's config says \`server\`, and \`hub deploy\` adds the hub half)`, and a real run keeps the past tense. The gate now measures the dry-run wording exactly (`case_hub_deploy/uniondry/role`, `grep -qxF`), which the old case could not: its only dry run was hub-on-hub, where the parenthetical never prints. ADR-0077 D4 records the wording as the mechanism. |
| S2 | **major** — `docs/stories/README.md:199` lost ADR-0076's summary and ADR-0077's bullet was given it | **Fixed.** The insert anchored on the bullet's *link* rather than the end of its line, so the new bullet landed between the link and its own em dash. ADR-0076's summary is restored on its own line and ADR-0077's bullet follows it; both were read back (`:199`/`:200`), the count is 77 bullets for ADR-0001…0077, and `docs/notes.md` now names the shape of the mistake (anchor on `(HS-0nn).`, which is how every bullet ends). |
| S3 | **major** — "`case_hub_deploy` needs no `openssl`" is false, in three documents | **Fixed, and the deeper question answered rather than dismissed.** Step 2 generates the VAPID pair with `openssl ecparam` and step 7's `doctor --full` has an `openssl` finding that is a *failure* when the program is not runnable, so the case dies at `run/exit` rather than taking its `SKIP`. The three claims now say "needs no **daemon** and no **image**" and name `install`/`chmod`/`df`/`openssl` as the real programs. The reviewer's aside — should a hub drop the `openssl` finding like it drops Docker and git? — is **refused with a reason**: `hosts::probe` runs `s_client` for every `https` registry row, so a hub without `openssl` cannot reach a peer at all, which is the whole of its registry's reachability. Recorded in `docs/notes.md` so the carve-out is not widened by a later story that reads only the Docker/git precedent. |
| S4 | **minor** — `unit_text`'s doc says "exactly two facts" and the function takes three | **Fixed**: "exactly three facts — where the binary is, whether this is a privileged install, and the role the machine will hold". |
| S5 | **minor** — a hub's satisfied clause reads as a fact about the user, not about this run | **Fixed**: "the service user `holosmith` exists, and this run joined it to no group because a hub drives no daemon". The doc above it now says why the subject matters (nothing removes a membership, so a `both` machine keeps the docker group). |
| S6 | **minor (Middle Man)** — `commands::hub::run_deploy` decides nothing and its doc says it does | **Fixed**: deleted; `main` dispatches `HubAction::Deploy` straight to `commands::deploy::run`, and `commands::hub` keeps only the registry half. `commands/hub.rs`'s module doc says why there is no wrapper. |
| S7 | **nit** — "the origin's own **authority**" where the code sends a host | **Fixed**: `client.rs`'s module doc and the `host` field say **host**, without the port, and note that `guard::host_of` strips one anyway. ADR-0077 D2's table row says the same. |
| SPEC-1 | **minor** — B5's "health" is the last probe's, and the spec's `status` row still reads "last health of registered machines" | **Fixed in the authority**: the row now says "— the registry row's own, as old as the boot; `status` makes no live hop". ADR-0077 D6 already recorded the refusal to fan out; the spec was the missing sentence. |
| SPEC-2 | **minor** — the spec's step-7 sentence and the `hub host` Commands row were not amended to match the code | **Fixed**: step 7 now says the next steps follow the role (`key set` on a machine that runs sessions, `hub host add` on one that forwards, and a server registers *into* a hub); the `hub host` row spells `remove <name> [--force]` and says `--force` is the API's `?force=true`. Both were already recorded in ADR-0077; the spec is the place an operator reads them. |
| OBS-1 | unfiled — `status::machines` repeats `counts`' open/missing/failed shape (~12 lines) | **Dismissed, with a citation.** `counts`' sentences name *sessions* and `machines`' name *the registered machines*; the shared rule is `db::Reader::open`'s (`NotFound` is "never served", anything else is an error — HS-050 T2), which already has one home. Factoring the two into a generic would put a `what` string in front of two different reads to save four lines, and the second block's doc points at the first. |
| OBS-2 | unfiled — a `MAX_ANSWER` truncation is reported as "something else is on that port" | **Fixed**, because the sentence blamed the answer for this client's own cap: the read now carries `capped` and answers `{method} {path} on {addr} answered more than this client reads (262144 bytes) in one answer`. |

Two things the review recorded as *clean* and that are worth keeping visible: the guards' four checks against the
request the client really writes (including `Content-Length: 0` on a `DELETE` and the content type only on a non-`GET`),
and the `"\nmachine "` (not `"machine "`) assertion — a substring check over a report whose keys are prefixes of one
another would prove nothing, which is the shape HS-072's own `status` test had to be fixed for.
