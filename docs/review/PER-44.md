## Standards

### Correct

- **The lock rule holds by construction, not by discipline.** `Transitioner::apply` (`sessions/state.rs:355-411`) does the read, the table lookup and the write inside one synchronous block that closes at `state.rs:386`; `events.append(...).await` is outside it (`state.rs:397`). The guard is `!Send`, so a future that held it across the await would not compile at `tokio::spawn`'s `Send` bound. Same shape as `provisioner.rs:181-196`.
- **The read and the write are one critical section**, so the illegal-move check has no TOCTOU: `get` (`state.rs:363-366`) and `set_status` (`state.rs:383-387`) are both under the one mutex, and `to` is taken from the row read back (`(current.status, updated.status)`, `state.rs:388`), not from the table.
- **The event writer is still the only path into the log, and the event follows the commit-triggering write.** `state.rs:389-407` — payload built after the block, `EventWriter::append` (`events/mod.rs:82-87`), nothing touches SQL from `state.rs` (and the sessions guard in `repository.rs:263-291` would catch it).
- **`AppState`'s one-wiring seam is respected.** `AppState::transitioner()` (`http/app.rs:72-80`) mirrors `provisioner()` and hands out both handles together; `Routes`/`App` untouched.
- **A refusal cannot leak into an ADR-0008 envelope.** `StateError::Illegal` is documented "A bug at the caller, never a client error" (`state.rs:283-286`) and no handler maps it yet — the right shape for HS-018+.
- **The provisioner's copy of the state logic is gone, not duplicated.** `settle`/`fail` (`provisioner.rs:112-121`) now call `Trigger::PiReady`/`Trigger::ProvisioningFailed`; `StatusPayload` and the local `set_status` are deleted (`diff` hunk at `provisioner.rs:16-55`), and `SESSION_STATUS` has exactly one definition (`state.rs:34`).
- **Test hygiene on the new suite.** Each test owns its `TempDir` (`tests/state_machine.rs:88,130,159,207,244` use distinct labels), one `Database::open` per path via `state_with_writer`, `expect` everywhere, and the writer is waited on rather than raced (`committed_events`, `state_machine.rs:66-85`).
- **`scripts/verify.sh` gets its `case_*`** (`verify.sh:278`, `570-592`) and `case_provisioning_steps` was updated in the same commit (`verify.sh:550,561`), so the story does not leave a red case behind. `docs/build.md:120-123` documents it; `docs/stories/README.md:117,134` bumps the ADR count and lists ADR-0016.
- **No stale consumer of the old payload.** Grepping the tree for `"status":"` in event assertions leaves only session-row JSON (`tests/sessions_api.rs:116,498`, `http/sessions.rs:504`, `verify.sh:464`) and ADR-0015's historical text; `web/` reads no event payload at all.

### Findings

- **should-fix** — `crates/holosmith/src/sessions/state.rs:626-672`: the guard that enforces item 2 is not proved to be *wired*, and its planted test re-implements the matcher instead of sharing it. `no_status_write_outside_the_one_function` walks the real tree and only asserts `offenders.is_empty()`; it never asserts the walk found anything, so a `sources_under` that returned `[]` (bad `CARGO_MANIFEST_DIR`, unreadable files) leaves it green — the exact defect PER-39 S2 fixed, whose precedent assertion is still in the neighbouring guard: `repository.rs:337-345` ("the walk did not find {root:?}/{REPOSITORY}"). And `the_guard_fires_on_a_planted_write` (`state.rs:654-672`) copies the skip-list-free loop by hand, so weakening the real rule (e.g. changing `text.contains("set_status")`) does not fail this test.
  *Fix:* extract `fn status_writes_under(root: &Path) -> Vec<String>` next to `THE_ONE_FUNCTION`/`REPOSITORY`, call it from both tests, and add the non-vacuity assertion that the walk contains `sessions/repository.rs` and `sessions/state.rs`. Same shape as `Guard::offenders_under`.

- **should-fix** — `GLOSSARY.md:98` and `docs/adr/0016-...md:82-94` overstate what is enforced. The glossary now says "no production code writes the column outside the one function that applies it", and the ADR says `apply` "is the only production caller of the repository's status write". Both are true of `set_status` only; the create writes the column too — `INSERT` carries `status` (`repository.rs:26-30`) and is passed `super::state::initial_status().as_str()` (`repository.rs:85`) — and the guard exempts `sessions/repository.rs` **as a whole file** (`state.rs:637`), so any second status-writing method added there passes the guard and the sessions SQL guard. The value being table-derived makes the code defensible; the prose is what is wrong.
  *Fix (docs only):* word it "no production code changes an existing row's `status` outside the one function", and add one sentence to ADR-0016 naming the create's insert as the other write site and why (`From::None` has no row to apply to). Optionally extend the guard to assert the only `status`-writing spellings in `repository.rs` are `INSERT` and `UPDATE_STATUS` (`repository.rs:26,33-34`).

- **nit** — `crates/holosmith/src/sql.rs:241-243`: `Guard::sources_under(&self, root)` is now a wrapper that ignores `self`, and it carries a duplicate of the free function's doc (`sql.rs:163-168`). One call site (`repository.rs:337`). Deleting the method and calling `sources_under(root)` is a two-line change. (Not a `-D warnings` risk: `clippy::unused_self` is pedantic-only.)

- **nit** — `crates/holosmith/src/sessions/state.rs:121`: `pub enum From` shadows `std::convert::From` throughout the module. Nothing breaks today (no `From` impl or `.into()` in the file), but the first `impl From<RepoError> for StateError` written here resolves to the local enum and fails confusingly — and the type is exported from the crate root path `holosmith::sessions::state::From`. `Source`/`FromStates` reads the table's column just as well.

- **nit** — `crates/holosmith/src/provisioner.rs:118`: `fail(&self, session, _step: Step, reason)` keeps a parameter it no longer uses (the transition carries `step: null` by design). Drop `_step` and the argument at `provisioner.rs:83`.

- **note** — `crates/holosmith/src/sessions/state.rs:389-397`: the write and its event are not ordered under one lock. The state is written inside the block and appended after it, so two concurrent `apply` calls on one session can enqueue their events in the opposite order to their writes (the writer assigns seq from queue order, ADR-0013:87-90), leaving a replay that ends on a stale state. Unreachable today — one provisioner task per session, called sequentially — so it is not a bug, but twelve stories will call `apply` and ADR-0016 should say it out loud. Smallest fix: one sentence in the ADR's "One function" section, or a `// Events from one session are ordered by whoever wins the append; HS-0xx owns per-session sequencing.`

- **note** — `crates/holosmith/src/provisioner.rs:161-162`: `announce` hard-codes `Status::Starting` rather than reading the row, so the payload's `from`/`to` is the one place the event does not reflect stored state. Correct today (provisioning only runs from `created`/`starting`) and the module doc states the rule; worth a `// only true while provisioning starts from starting` so a resume-then-provision story does not inherit a lie.

- **nit** — `docs/build.md:120-123`: the added clause makes "…the backend the boot chose (`case_backend_from_config`), and the provisioning that create starts (…), and the state machine's payload (…)" — a double "and" in one list — and its final line runs past the ~95-column wrap the surrounding prose keeps. Reflow to "…, the provisioning that create starts (…), and the state machine's payload (…)".

- **note (counts, unverified)** — ADR-0016:102 claims "20 cases, 60 assertions". My reading of the script gives exactly that: the new case contributes `expect_status` (`verify.sh:108-110` → `check` → +1), `check last_payload` (+1), the `case` branch (+1), and one more `expect_no_cors` from the CORS sweep over the newly saved `.http` (`verify.sh:596-602`); 19/56 → 20/60. Reasoned, not observed.

## Spec

Acceptance items 1–6 of HS-012, judged against the code.

**Item 1 — the table is the spec's table, in one place: verified, with one deviation.**
`TABLE` (`state.rs:158-234`) against `HolosmithSpec.md:141-153`, row by row: `none→create_accepted→starting` ✓ (141); `starting→pi_ready→idle` ✓ (142); `starting→provisioning_failed→error` ✓ (143); `idle→prompt→running` ✓ (144); `running→agent_settled→idle` ✓ (145); `running→abort_completed→idle` ✓ (146); `running→abort_ladder→stopped` ✓ (147, second row `stopped→resume` at 149, documented at `state.rs:140-149` and ADR-0016:23-30); `idle→evict|idle_stop|drain→stopped` ✓ (148, three rows); `stopped→resume→starting` ✓ (149); `starting|idle|running→unexpected_exit→error` ✓ (150); `error→resume→starting` ✓ (151); `any→delete→deleting` ✓ (152); recovery ✓ in target and in the deferral of "then idle" to the `pi_ready` row. `Trigger::ALL` is 14 and every trigger appears in the table (`state.rs:481-502`), and `the_table_is_the_specs_table_row_by_row` (`state.rs:497-...`) pins all 15 rows in spec order. The deviation is the recovery row's `From`, below.

- **should-fix** — `crates/holosmith/src/sessions/state.rs:229-233` and `docs/adr/0016-...md:17-18`: the recovery row is `From::Any`, and the ADR justifies it with "because the spec's table says "any" for delete **and crash recovery**". The spec says no such thing: only the delete row is `any` (`HolosmithSpec.md:152`); the recovery row's From is "server crash" (`HolosmithSpec.md:153`). The story's test comment repeats the misquote (`state.rs:559-562`: "because the spec's recovery row is `any`"). Consequences that the ADR does not weigh: `apply(CrashRecovery)` is legal from `stopped` and `error`, and from `stopped` it goes through `set_status`, which clears `stopped_at` (`repository.rs:165`) — i.e. a startup reconcile that walked every row would restart item 15's 7-day retention clock and re-count a stopped session as live, which items 7 and 15 argue against. The deferral of that choice to HS-044 exists only as a test comment, not as an ADR bullet.
  *Fix:* make the row `From::OneOf(&[Status::Starting, Status::Idle, Status::Running])` — the spec's own live set, and consistent with "a running turn is recorded as `interrupted`" — or, if `Any` is kept, replace the false clause at ADR-0016:17-18 with "the recovery row's From is the situation 'server crash', which this table reads as `any`; HS-044 narrows it" and say so in the ADR body, not only in a test.

**Item 2 — one function, direct writes impossible: verified with the two limits recorded above.**
`apply` is the only production caller of `set_status` (`state.rs:383-387`; the only other `src/` mentions are the definition at `repository.rs:159-178` and its doc), and the guard test asserts that over `src/**`. See the two Standards should-fixes for what the claim over-reaches: the create's `INSERT` writes the column (`repository.rs:26-30,85`) and `repository.rs` is exempt wholesale, and the guard's wiring is not proved non-vacuous. The crate-boundary half of the argument is sound: `tests/session_repository.rs` and `tests/state_machine.rs` are outside `src/` by construction, they call the repository to set up fixtures the way HS-007 needs, and nothing in `src/` gains an escape hatch for them.

**Item 3 — an illegal move is logged with from/to/trigger and refused: verified, with the agreed caveat.**
Refusal path: log at `error` with `session`, `from`, `trigger` (`state.rs:367-375`) *before* any write, then `Err(StateError::Illegal)`; nothing is written and nothing is emitted (`tests/state_machine.rs:88-127` asserts the row is byte-identical after each refusal and the log is empty). Applied path logs all three (`state.rs:404-411`). The missing `to` on a refusal is the decided design and ADR-0016:52-63 says so in as many words — the implementation is consistent with it.

**Item 4 — events carry from, to and optional reason; `status_reason` persisted: verified.**
`SessionStatus { from, to, step, reason }` with explicit nulls (`state.rs:309-345`), pinned by `the_payload_is_four_keys_in_order_with_explicit_nulls` (`state.rs:590-608`); the transition's payload is built from the states the row actually held (`state.rs:389-396`); the reason reaches the column through `set_status`'s `status_reason` (`repository.rs:33-34,166-172`) and is asserted persisted in `tests/state_machine.rs:186-190,226-230` and in the provisioner's failure test (`tests/provisioning.rs:316-320`).

**Item 5 — `stopped_at` set on entering `stopped`, cleared on resume, in the same function: verified.**
It is in the *same statement* as the state: `let stopped_at = (status == Status::Stopped).then_some(now)` (`repository.rs:165`) feeds `UPDATE_STATUS` (`repository.rs:33-34`), which `apply` calls at `state.rs:383-387`, so there is no window in which a `stopped` row lacks `stopped_at` and no path can move the state without moving the column. Both directions proved end to end through `apply` at `tests/state_machine.rs:157-204` (`stopped_at` set on `idle_stop`, cleared on `resume`), on top of HS-007's repository-level proof.

**Item 6 — `ended` does not exist; `interrupted` is a reason: verified.**
`Status` has the six variants and only those (`sessions/mod.rs:19-46`), `FromStr` refuses anything else (`sessions/mod.rs:62-70`), no row reaches a seventh state (`state.rs:534-543`), and a tree-wide grep for the word `ended` in code finds it only in prose, in tests that prove it is refused (`repository.rs:327-336`, `tests/session_repository.rs:391-413`), and in the two new comments saying it does not exist. `interrupted` is carried as the crash-recovery row's reason in `tests/state_machine.rs:207-241`.

- **nit** — `GLOSSARY.md:113-114` (**Resume**: "Bringing a stopped session back to `idle`") still contradicts the table this story makes authoritative: the row is `stopped → starting` (`state.rs:216-220`, `HolosmithSpec.md:149`), and `idle` comes later via `pi_ready`. The story adds three glossary entries and is the moment to reconcile this one line: "Bringing a stopped session back — the `stopped`+`resume` row to `starting`, then provisioning to `idle`". - **nit** — `crates/holosmith/tests/state_machine.rs:97-99`: the demo ("a test attempts each illegal transition") is exercised against `starting` only at the database level; the exhaustive 6×14 matrix lives at `lookup` level (`state.rs:546-557`). ## Merge verdict
