**The five concurrency questions, answered from the tree** (all five hold):

1. **`std::thread`, not a tokio task** — `src/events/writer.rs:31-35` spawns via `std::thread::Builder`, and the loop uses `incoming.blocking_recv()` (`:53`), which panics on a runtime worker, so the choice is enforced, not just documented.
2. **Seq from `sessions.last_seq`, same transaction** — `src/events/repository.rs:56-60` bumps and reads back through `SessionRepository::bump_last_seq` (`src/sessions/repository.rs:40`, `UPDATE … RETURNING`) inside the `unchecked_transaction` that also does the INSERT (`:47-77`). `MAX(seq)` appears only in `LATEST` (`:26`), never in assignment. The deletion case is tested: `tests/events.rs:304` deletes every row via a second connection and asserts the next seq is 4.
3. **Broadcast strictly after COMMIT** — `writer.rs:55-77`: `commit()` returns the assigned vec (its `transaction.commit()` is `repository.rs:75`), then `events.send(event)` per event in order. `tests/events.rs:343` proves it with `reader(&dir)`, a second `Connection`, not by counting rows.
4. **A slow subscriber cannot delay or fail the commit** — `broadcast::channel(1024)`; `Sender::send` never waits; the `Err` with no receivers is discarded (`writer.rs:75`, `let _ =`). Producers get the bounded queue instead (`PRODUCER_QUEUE`, `writer.rs:19`).
5. **The two guards stay quiet about each other** — verified exhaustively: the only `sessions` statements are in `sessions/repository.rs` (incl. `:40`), the only `events` statements in `events/repository.rs`, and neither file's prose normalises to the other's phrase (`events/repository.rs:6` says "on `sessions`", not "from sessions"). `events/repository.rs:373`'s walk skips only its own file; both pass over today's tree.

## Standards

- **S1 — should-fix (test isolation).** The new guard's `TempDir` collides with the sessions guard's in the same test binary. `src/events/repository.rs:151` and `:208` use the labels `"planted"` and `"spelling"`, exactly as `src/sessions/repository.rs:342` and `:399` do, and both helpers build the path as `holosmith-guard-{label}-{pid}` (`events/repository.rs:373`, `sessions/repository.rs:580`). Same crate ⇒ same lib-test binary ⇒ same pid ⇒ **the same directory**, and both plant a file named `planted.rs` with table-specific SQL, while `TempDir::new` starts with `remove_dir_all`. Under the default parallel harness one test can delete or overwrite the other's fixture mid-run, so `the_guard_fires_on_a_planted_statement` intermittently fails with `[]` or the other table's phrase. This breaks the repo's own stated rule — `tests/support/mod.rs:26-32`: "two binaries that use the same label … would `remove_dir_all` each other's live directories". Smallest fix: two string literals (`"events-planted"`, `"events-spelling"`). Repro for the supervisor: `for i in $(seq 20); do cargo test --lib -- repository::tests || break; done`.
- **S2 — should-fix (Duplicated Code, judgement call).** `src/events/repository.rs:216-393` is a near-verbatim copy of `src/sessions/repository.rs:405-601`: `offenders_under`, `names_word`, `normalise`, `squashed`, `rewrite`, `is_word`, `sources_under`, `TempDir`. Only the table word and the doc examples differ. A fix to one matcher will not reach the other (they have already drifted: the sessions `squashed` carries a five-line `\`-continuation comment the events copy lacks). The repo has precedent for consolidating this exact helper (`tests/support/mod.rs:26` records "PER-39's third copy"). Smallest fix: one `#[cfg(test)]` helper parameterised by `(table, statements, repository)` — which also removes S1's root cause, since a shared helper would take the label as a parameter. Cheap and worthwhile now, before HS-060 adds a third table.
- **S3 — should-fix (invariant is unenforced).** `EventRepository::insert_batch` (`events/repository.rs:47`) and `SessionRepository::bump_last_seq` (`sessions/repository.rs:178`) are both `pub`, so "exactly one writer assigns seq" is convention only: anything holding the `Arc<Mutex<Database>>` can insert an event, or bump the counter alone and leave a permanent gap. `bump_last_seq` has exactly one caller (`events/repository.rs:56`), so `pub(crate)` is free. `insert_batch` needs `tests/events.rs:500` and `:538` moved behind a `#[cfg(test)]` seam first (they exercise the refusal path, which the writer swallows), which is why I am not calling this a blocker.
- **S4 — nit.** `migrations/0003_events.sql:17`'s `events_session` index duplicates the index SQLite already builds for the composite primary key — the comment on `:16` says so. It costs a second b-tree write on every event row, on the story's durability path, and exists so `scripts/verify.sh:283-286` has a name to grep. Either drop it and grep `sqlite_autoindex_events` (stable, derived from the table name), or make the table `WITHOUT ROWID`.
- **S5 — nit (documentation drift, not the decision).** ADR-0012:25 ("HS-009 replaces this `Mutex` rather than living beside it") and :72 ("HS-009 removes it") now assert the reverse of ADR-0013 and of the shipped code. The diff correctly rewrote the same sentence in four code comments (`db.rs`, `app.rs`, `serve.rs`) but left the ADR a reader would consult. One "superseded by ADR-0013" line at each. This is the class `docs/review/PER-40.md:66` (S2) already ruled on.
- **S6 — nit.** `tests/events.rs:343` proves commit-before-broadcast probabilistically: with a broken send-before-commit the read only misses if the commit loses a microsecond race. Deterministic version: give the writer a long `commit_interval`, `append`, then assert a short `tokio::time::timeout` on `recv` yields nothing while `committed(&connection, …) == 0`, then let the window expire and assert both the event and the row appear.
- **S7 — nit (Mysterious Name).** `EventRepository::latest_seq` (`events/repository.rs:94`) answers `SELECT max(seq)` (`:26`), i.e. the newest *visible* seq, which compaction moves backwards — in a story whose central rule is "never derive the counter from MAX(seq)". The doc comment warns, the name does not. Rename to `newest_visible_seq` (or drop it until HS-010 needs it; it has no production caller today).

**Standards verdict: OK with notes.** No behavioural defect in a shipped path. S1 is a real intermittent test failure and costs two string literals — worth doing before merge; S2/S3 should land before HS-010/HS-011 build on this seam.

## Spec

- **P1 — should-fix (the broadcast half is unreachable in the shipped binary).** `spawn` returns the only `EventStream` (`writer.rs:28-41`) and hands the `broadcast::Sender` into the writer thread (`:51`); `EventWriter` holds only the mpsc sender (`mod.rs:63-64`), and `serve.rs:119` drops `_stream`. There is therefore no `subscribe()`, no retained sender, and no way to obtain a subscriber handle later — HS-010 must change `events::spawn`'s signature or `EventWriter`'s fields. Acceptance ("only then broadcasts, in order") is implemented and tested in-process, but in the app the channel has zero reachable receivers by construction. Smallest fix: keep a `broadcast::Sender<Event>` clone in `EventWriter` and add `pub fn subscribe(&self) -> EventStream`. (The absence of a *subscriber* today is the recorded decision; the absence of a way to *make* one is not.)
- **P2 — should-fix (acceptance bullet is unfalsifiable as proved).** "WAL and `synchronous=FULL` are asserted at startup, not assumed" rests on `db.rs:243-246`, whose read-back cannot fail for `synchronous`: the pragma is per-connection and SQLite's default is already FULL(2), so a `pragma_update` that silently did nothing still reads back `2`. The new test then re-asserts `2` on a *fresh* second connection (`tests/events.rs:211-212`), where it is trivially true — the test's own comment concedes this. `journal_mode` is genuinely proved (`:210`, and WAL survives in the file). Smallest fix: say plainly in ADR-0013 and at `db.rs:243-246` that the `synchronous` read-back distinguishes "the statement errored" from "it did not", not FULL from SQLite's default, and drop the tautological assertion at `tests/events.rs:212` (or make it falsifiable by setting a non-default value first).
- **P3 — nit.** ADR-0013 records that a failed batch is rolled back and dropped, and that an event naming a missing session refuses the batch (`UnknownSession`). What it does not state is the collateral: one such event discards every *valid* event in the same 25 ms batch, from any session, after `append` already returned `Ok` (`writer.rs:55-69`). Unreachable today (no producers); HS-011 makes it reachable. Either record the collateral in the ADR or skip just the offending event (`insert_batch` per-event isolation, or a pre-check).
- **P4 — nit.** The plan ("The observable rule", item 3, and step 9) promised "the automated test drives the real binary the way `tests/serve_cli.rs` does" for the `kill -9` demo. No such test exists — `tests/events.rs` has no process-level case and no `kill`. The demo's *subject* (library vs shipped binary) is the disclosed decision, so this is only about the in-repo automation the plan claimed and the tree lacks.
- **P5 — nit.** Spec item 5's rationale — "a restarted seq counter would make clients drop new events" — is half-proved. `the_durability_rule_holds_across_a_reopen` (`tests/events.rs:426`) reopens the file and reads rows, but never appends after the reopen, so nothing asserts that the *counter* (not the rows) survived. Two lines: append one event after reopening and assert `seq == 4`.

**Spec verdict: OK with notes.** Every acceptance box is implemented, and the crash-consistency claim genuinely holds — commit-then-broadcast, a durable column counter bumped in the same transaction, and `send` that cannot block a commit. P1 and P2 are about the claim being *reachable* and *falsifiable* rather than about the mechanism being wrong.

---

**Merge verdict: OK with notes.** S1 (temp-dir collision) and P1 (`subscribe()`) are the two I would fix before merge — both small and both about the seam HS-010 lands on next.
