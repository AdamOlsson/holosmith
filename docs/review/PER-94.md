The `Cow<'static, str>` change (`http/error.rs:201-206`, `:237-243`, `:527-530`) is minimal and its claims check out: `&'static str` callers still convert, the serialised bytes are unchanged, the one non-literal construction is `ApiError::disk_floor` (`error.rs:609-624`), and `internal` keeps its fixed sentence so ADR-0012's rule is intact (`error.rs:654-664`, `:717-725`). `spawn_blocking` guards the one subprocess on the request path (`http/sessions.rs:378`). `docs/stories/**` is touched only at the permitted ADR index.

- **Finding P2 — the refusal sentence describes only the create, and the constructor's doc says otherwise.** `ApiError::disk_floor`'s doc claims "The **message is this request's own**" (`error.rs:602-607`), but the one sentence is shared and says "... so no new session is started ..." (`error.rs:611-616`), while it is also the resume's answer (`sessions.rs:911-913`). A resume starts an *existing* session, so the clause is false for that request — the rule the same doc comment invokes ("a message must describe its own request"), and the reason `cap_reached`/`cap_without_idle` are two sentences on one code (`error.rs:626-638`). Smallest fix: drop *new* — "so no session is started" — which is true of both requests, and leave the code and its single-sentence justification alone.
- **Finding P2 — `case_disk_floor` stops the phase's shared boot and never puts it back.** `verify.sh:7059` stops it, `verify.sh:7089` boots its own, `verify.sh:7183` stops that one, and there is no `start_serve` before the `}` at `verify.sh:7188` — while every peer that reboots the shared fixture restores it and says why (`verify.sh:4153-4155`, `verify.sh:8230-8231`, `verify.sh:8380`, `verify.sh:8654-8655`). The case's own comment therefore overstates ("It leaves behind only its scratch root and the socket pid it kills", `verify.sh:7049`): it also leaves `serve_pid=""` and a dead `$port`/`$control_origin` for the cases that follow in `serve_cases` (`verify.sh:436-438`), and `stop_serve` fails hard on an empty pid (`verify.sh:8714-8716`), so today's green run depends on `case_status` happening to restart the boot later (`verify.sh:8380`) and on `case_doctor_full`'s unguarded `stop_serve` (`verify.sh:8127`) running after it. Smallest fix: `stop_serve` + `start_serve` at the end, like `case_drain` and `case_status`.
- **Finding P3 — the ADR index count is now wrong.** `docs/stories/README.md:188` adds the 68th ADR bullet; `docs/stories/README.md:117` still says "Sixty-seven decisions were made". Smallest fix: "Sixty-eight".
- **Finding P3 — the new ADR contradicts itself on its own count.** `docs/adr/0068-...md:9` says "Four decisions", then D1–D5 follow at `:11`, `:37`, `:62`, `:77`, `:83`. Smallest fix: "Five decisions".
- **Finding P3 — `min_free_gb = 0` still requires a working `df`.** ADR-0068 D4 (`:77-81`) and `GLOSSARY.md:214-215` say `0` means "no floor", but `disk_floor` measures first and returns a 500 for `DiskError::Unrunnable` (`sessions.rs:372-383`), so a `0`-floor machine without `df` refuses every create with 500 rather than not measuring at all. `tests/disk.rs:412-424` (`a_floor_of_zero_is_no_floor`) cannot see this because its shim works. Smallest fix: `if state.config.min_free_gb == 0 { return None }` before the measurement (or one clause in D4 saying the floor's absence still needs the reader).
- **Finding P3 — `AppState::preflight` is a name for programs, not for the check.** `http/app.rs:88` holds `preflight::Tools`, i.e. the external programs; every other use of "preflight" in `GLOSSARY.md:15-25` names the *check*. `state.preflight.df` (`sessions.rs:376`) reads ambiguously beside `preflight::check`. Smallest fix: rename to `tools` (Mysterious Name; judgement call, and no behaviour changes).

## Spec

**Correct.** Item 14's first sentence is implemented as asked (507 + `disk_floor`, `error.rs:598-624`), the check precedes every effect on both paths (`sessions.rs:279-285` before `slot_for`; `sessions.rs:911-913` before `refuse_project`, the cap and `apply_trigger`), the idempotent replay still answers its own row, and nothing is created on refusal — witnessed rather than promised (`tests/disk.rs:300-345`: zero rows, no worktree). The measurement really is one: `disk::measure` is named twice outside `disk.rs` (`preflight.rs:528`, `sessions.rs:378`) and nowhere else in `src/`, so "one number" is structural, and `doctor` fails the disk line from the same call (`verify.sh:7178-7185`). The D3 qualification (Docker and not a `hub`) is defensible, not a hole: it is `preflight::check`'s own documented predicate (`preflight.rs:262-267`) one level down, it matches the established `runtime.backend` seam (`http/app.rs:212-220`), a stub session provisions nothing (`backend/stub.rs:361-367`), and it is what keeps the "the two never disagree" bullet true for the run that matters.

- **Finding P2 — acceptance bullet 3 holds only for measured runs, and the diff's own new test is the counter-example.** `doctor::run` never consults the backend (`doctor.rs:204-213` skips only Docker/Git on a hub), so on the config `tests/disk.rs:412-424` builds — `min_free_gb: 1_000`, an answer of 0 GB, stub runtime — `doctor --quick` reports `disk: fail` while `POST /api/sessions` answers 202. Neither ADR-0068 D3 (`:62-75`) nor `GLOSSARY.md:212-224` records that split, although the test exists to show it. Smallest fix: one sentence in D3's consequences — "on a `stub` run `doctor` still fails the disk line and the request paths do not, because only a container run is measured" — so the acceptance's limit is stated rather than implied.
- **Finding P2 — the "structural" guard is file-granular and exempts the turn's own handlers.** `disk.rs:205-207` allow-lists whole files, and `THE_REQUEST_PATHS = "http/sessions.rs"` is also where `prompt`, `abort` and `steer` live (`sessions.rs:731`, `:787`, `:823`). So the claim at `disk.rs:210-215` — "a turn, a ladder, a sweeper or a provisioner that grew a disk read would fail here" — is false for the most likely place such a read would be added: the turn's own request handler. The matcher also tests one token, so a hand-rolled `Command::new("df")` anywhere passes. The guard is non-vacuous and its non-vacuity assertion (`disk.rs:236-246`) and planted test (`:252-266`) are real; only the exemption's shape is wrong. Smallest fix: allow the two handlers rather than the file — move `disk_floor` into `src/disk.rs` as an `AppState`-taking helper in a new `src/http/...` module, or assert per line — so `http/sessions.rs` stops being a blanket exemption.
- **Finding P3 — no witness that a create at the cap refuses without evicting.** `create_locked`'s doc claims the refusal is raised between the key's lookup and the cap "because a create that cannot run must answer its own refusal rather than stop somebody else's session" (`sessions.rs:571-573`, honoured at `:279-285`), and ADR-0068 D1 says the same; nothing exercises the floor *at* the cap (`tests/disk.rs` uses a free slot; `verify.sh:7085` sets `max_live_sessions = 3` with one row). Smallest fix: one test with `max_live_sessions: 1`, an idle row and a short answer asserting 507 and that the idle row is still `idle`.
- **Finding P3 — the "one number" test cannot see a second number in a handler.** `tests/disk.rs:245-261` compares `preflight::report_with`'s sentence with a direct `disk::measure` call, not with what `POST /api/sessions` computed; a handler with its own parser and divisor would pass it (the 507 tests at `:264-300` are the real witnesses). Smallest fix: drive the boot and the create in the same test and compare the two numbers.
- **Finding P3 — the measurement runs on an idempotent replay.** ADR-0068 D1 (`:31-33`) says the refusal is deferred past the key lookup; true of the answer, not of the work — the create forks `df` before `slot_for` (`sessions.rs:281-285`), so the replay path in `tests/disk.rs:355-380` pays a subprocess it discards. Judgement call; a one-line note in D1 is enough.

Not verifiable from the supplied artifact: the two commits, their conventional form, `Closes PER-94`, and the Linear body/plan comment. `watchdog_diff` does not inspect committed ranges and the tree is clean, so those claims need the commit log; the identifier itself is consistent with `RESUME.md:1,48,1146` (PER-94 = HS-062) and `RESUME.md:208` (0068 was the next free ADR).
