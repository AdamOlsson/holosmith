**S1 — the P1.** `tests/schema_previous.rs:127-133`:

```rust
    assert_eq!(
        then.keys().collect::<Vec<_>>(),
        now.keys().collect::<Vec<_>>(),
        "the snapshot and this build disagree about which tables exist — one was dropped, or the snapshot was \
         refreshed from another build ({})",
```

`then` is the snapshot, `now` is this build. Equality rejects a table in `now` that is not in `then` — an **added table**, which is the one thing the rule permits. Four independent statements of intent say so and one of them condemns this line in as many words:

- `tests/schema_previous.rs:13-15`: "the snapshot must name every table this build has" — a superset test, not equality.
- `tests/schema_previous.rs:191-193`: the comparison function's own test asserts an `added_later_table` is **invisible** to `missing`, with `missing(&then, &wider).is_empty()` at `:198`. So the function tolerates what the guard forbids.
- `docs/adr/0047-…:41-42`: "The test is a **subset**, because adding is the point: a test that demanded equality would forbid the rule it checks."
- `GLOSSARY.md:625-626`: "every table and column it names must still exist, so a drop or a rename fails and **an addition does not**"; `docs/build.md:331`: "A migration may **add**."

Why it bites and how soon: refreshing `docs/schema/previous.sql` is a **release step** (`docs/build.md:349-358`, ADR:65-71), so during development `then` is the previous release's schema and `now` is one table wider the moment any story adds a table. The case then fails with a message naming two causes — "one was dropped, or the snapshot was refreshed from another build" — neither of which happened, and the only repair the message implies (`docs/build.md:373-375`, the subset-failure text) is to refresh the snapshot from the *new* build, which silently voids the release-over-release check for the rest of that release. That is the shape this repo treats as a blocker: a guard whose repair path destroys what it guards.

Smallest fix — keep the intent, drop the direction:

```rust
    for table in now.keys() {
        assert!(
            then.contains_key(table),
            "the snapshot does not name {table}, so it is truncated or was refreshed from another build ({})",
            dir.path().display()
        );
    }
```

`missing(&then, &now)` still reports a dropped table (`:146-193` covers exactly that shape), so nothing is lost.

**SP1.** Story `:17`: "A release may **add** but never drop or rename anything the previous release uses." With `docs/schema/previous.sql` refreshed at release time (ADR:65-71), the first migration that creates a table makes `then.keys() != now.keys()` and the `migrations` phase goes red on a legal expand — and the message offers only "refresh `docs/schema/previous.sql`", which is the move that deletes the check for that release. Bullet 2 says "still a subset of the current one"; a subset relation is what should have been asserted, in one direction. Worst finding on this axis, and it is the same defect as S1: **one bug, two axes.**

**SP2 — honest, but the seed hides the gap.** `previous.sql:1` calls itself "The schema the **previous** release shipped"; `:20-21` calls itself "Snapshot of the schema **this build** leaves behind: schema 4"; `SCHEMA_VERSION` is `4` (`schema.rs:21`). Both headers describe the bootstrap seed, and they disagree. The test is therefore trivially true today, which is the "does it rot silently" question: `scripts/schema-snapshot.sh` accepts **any** migrated database (`:34-52` — it checks only that `schema_version` has a row), so a release engineer who runs it against the new build instead of the release being left gets a byte-identical file and a green gate, with the mechanism quietly disabled. Nothing in the gate notices an unrefreshed snapshot either: a stale file only names fewer columns, and the subset test cannot see what it was not told. This is the price of "no story owns it" (ADR:71) and the ADR does say the temporality is unenforceable — but the *seed* ambiguity is a fixable, one-line honesty problem: make both headers say which release the dump came from and that the initial file is this build's own schema until the first release step, and have the script refuse a database whose `holosmith` version equals the artifact's when the caller did not pass `--allow-same-release`.

**SP3 — the reduction is an acceptance, not an evasion, but the evidence is inverted.** `serve` continuing on a newer database is *required* by item 10 (`HolosmithSpec.md:203`: "That makes the symlink rollback safe without restoring the database"), and `doctor` refuses a start is a different moment; ADR-0047:73-79 separates them correctly and `schema::verdict` + `Verdict::sentence` are the right shape for HS-045 to consume. So bullet 3 is **partial by design, and the design is argued**. What makes it read like an evasion is that the story's observable — the only thing an operator or the gate can inspect today — is a sentence naming a command that does not exist, and `verify.sh:1964-1965` plus `tests/db_migrations.rs:434-439` lock the word `doctor` in place as though it did. Fixing S6 makes the reduction honest at no cost to the gate.

**SP4.** ADR-0047:56-62: "the three callers read it rather than comparing numbers themselves: `apply_pending` warns and continues, the banner prints the **recorded** number, and `doctor` (HS-045) is where the `Newer` sentence becomes a refusal." Two callers read `verdict`; the banner (`commands/serve.rs:382-386`) reads `Database::schema_version()`, which is the recorded number by construction (`db.rs:87-92`, `db.rs:302-321`) — so the claim's substance holds, its count does not, and `schema.rs:144-146` repeats it. Fix: "the banner prints the number the verdict is about".

**On the two things the brief asked me to judge hardest.** (a) The claim that the story built no scanner is **true and verifiable**: `schema::contract_violations` (`schema.rs:196-205`) refuses an unmarked `DROP TABLE`/`DROP COLUMN`/`RENAME`, its unit tests drive every arm (`:332-399`), `the_embedded_migrations_carry_no_contract_violation` (`:402-405`) runs it over the embedded set, and `cargo test` is the gate's third phase (`verify.sh:3674`) — so the demo bullet ("a CI check rejects a migration that drops or renames a column the previous release still reads") was **already met for the local half** before this diff. Building a second scanner would have been the duplication this repo refuses. What the demo's words add — "the previous release still reads" — is exactly the half this story built, and the two measured mutations in the brief show both halves firing on the same file with different names. That part is honest. (b) The file is a **subset** test as the ADR says (the `missing()` comparison), but it is wrapped in an **equality** guard that is not a subset test (S1/SP1) — so the sentence "a test that demanded equality would forbid the rule it checks" describes the shipped code's defect, written by the same change. That is the one place this deliverable is not honest with itself, and both axes land on it.

- **Standards:** 13 findings — worst **P1** (S1, the equality guard at `tests/schema_previous.rs:127-133`, which forbids a legal add and points its repair at the mechanism's own destruction). S2–S6 are one-line or one-paragraph fixes worth taking in the same pass. **BLOCK** until S1 is fixed.

Bullet 2 is met (with the seed ambiguity of SP2), bullet 3 is partial *by design and argued* (SP3/S6 is the honest form of the reduction), bullet 4 is met. **OK with notes** otherwise — no acceptance bullet is unaddressed, none is fabricated, and the "we built no scanner" claim is true.
- **Merge verdict: BLOCK** — on one defect, visible on both axes (S1/SP1), plus the operator-facing `doctor` sentence (S6). Fix those two, add the `rm -rf "$root"`, and refresh the gate's own description, and this is a good change: the half it claims to add is real, measured both ways, and correctly kept out of `migrations/`.
