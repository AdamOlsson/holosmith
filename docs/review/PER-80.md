### Correct (verified, not taken on faith)

- **The "no Holosmith labels" doctor arm is reachable through the *real* reader, and only through it.** `Docker::labels` (`src/images.rs:257-268`) asks `image_exists` first, so `Ok(None)` means "not there" and is a **fail** (`src/doctor.rs:770-779`); an image with no labels goes `{{json .Config.Labels}}` → `null` → `parse_labels` (`src/images.rs:286-291`) → empty map → `Ok(Some({}))` → `unbuilt` → pass-with-remark (`src/doctor.rs:781-789`). `tests/doctor.rs:148-166` fakes exactly `Ok(Some({}))`, not `Ok(None)`, so the test is not asserting an arm production cannot reach. A *partially* labelled image is not unbuilt (`unbuilt` is `all`, not `is_empty`) and is reported key by key.
- **The fourth label is genuinely load-bearing.** `mismatches` compares `LABEL_TOOLCHAINS` for the agent expectation only, and `tests/images.rs::a_mismatch_names_the_key_and_both_values` asserts the *same* map passes the proxy expectation — so a changed `agent_toolchains` is `Stale` and the proxy image is correctly not rebuilt. Not decoration.
- **The broken-build half builds the embedded const, not a copy**, into a test-only tag, and asserts the tag does not exist afterwards (`tests/images.rs:719`, `:770-792`). The proxy arm cannot collide with a deploy.
- **The new config key is registered where the repo's own recipe demands**, and the cheap cross-check is automatic: `the_table_and_the_struct_agree_in_both_directions` (`src/config/schema.rs:751-784`) fails on a field with no row, `KNOWN_KEYS.len()` is 33 (`:807`), the golden moved, and `EVERY_KEY` (`src/config/mod.rs:947`) gained the key with its assertion — so the "setter writes the wrong field" hole that PER-59-60 fixed is not reopened.
- **The `--user` fix is a real fix of a real failure**: it replaces "the base image happened to be uid 1000" with a fact read from the key file, and the test proves the machine it runs on can see the difference (`src/container.rs:1069-1101`).
- The tar is hand-written and verified by an independent reader (the `tar` program, `tests/images.rs::the_archive_is_a_ustar_the_tar_program_reads`); `pin_single_source` covers the new files automatically because it walks `git ls-files`.

### Findings

**P1 · spec axis (acceptance 3) · `crates/holosmith/src/images.rs:440` `read` / `:120-127` `Expectation::of` — the skip rule never reads the binary, so it answers `satisfied` over an image holding an older binary.** The expectation is three `env!` strings plus the toolchain list; the payload the build actually copies (`COPY holosmith`) is not represented anywhere. `HOLOSMITH_GIT_TAG` is `git describe --tags --always --dirty` (`crates/holosmith/build.rs::git_tag`, `scripts/build.sh:52`), which is *identical before and after a rebuild of the same dirty tree* — so edit `container.rs`, rebuild, `server deploy`: step 3 prints `satisfied` and `hs_egress` keeps running the previous binary. ADR-0057:111-113 justifies the omission with "the git tag already carries `-dirty`", which distinguishes clean from dirty, not one dirty tree from another. The gate cannot catch it: `scripts/verify.sh:5442` deletes the tags to force `changed`, which is precisely the compensation for a read that cannot see a binary change. Smallest true fix: a fifth label carrying a digest of the bytes `archive()` already reads (`org.holosmith.binary-sha256`), computed in `Expectation` and compared like the other four; if labels-only is kept, ADR-0057 and `docs/notes.md`'s landmine must say the read is blind to a rebuilt binary at the same `describe` and name what an operator does about it.

**P2 · spec axis (acceptance 5) · `crates/holosmith/src/images.rs:405,408` `failure` — "and nothing was tagged {image}" is untrue in the state this story's own landmine documents.** `docs/notes.md:1546-1550` says "if the tag already pointed at an older image, that image stays" — and that state is reachable on any rebuild that is not a version bump (a changed `agent_toolchains`, or the P1 above), so the failure sentence asserts the opposite of what happened. `tests/images.rs` only ever builds into a *fresh* tag, so the assertion cannot fail on it. Fix: `… and no new image was tagged {image}: {last}` (one word), plus the two assertion strings in `tests/images.rs::the_failure_sentence_…` and `:777-781`.

**P2 · standards axis (the gate) · `scripts/verify.sh:5064-5066` vs `:5084` — the case claims to own the absent state and never checks it, so it can pass having never rebuilt the proxy image.** `docker image rm -f "$proxy" "$agent" … || true` swallows the failure, and nothing asserts the tags are gone before the deploy. If the proxy tag survives — the normal cause being an in-use image, i.e. an `hs_egress` left running by an interrupted earlier run, since `cleanup()` (`verify.sh:124-132`) removes only `hs_images_*` — then step 3 rebuilds the agent image alone, still prints `changed`, and `grep '^3\. images: changed: '` at `:5084` is satisfied. `case_server_deploy` gets this right at `:5437` (it removes `hs_egress hs_key` *before* the untag). Fix: the same `docker rm -f hs_egress hs_key` before `:5065`, those two names in `cleanup()`, and `docker image inspect "$proxy" "$agent"` must fail before the deploy.

**P2 · spec axis (the container-user/key-store identity) · `crates/holosmith/src/container.rs:685-689` — `--user` is taken from the key *file*, but what the container has to traverse is the *directory* (`:648`), and no single `--user` satisfies both when their owners differ.** The store is 0700/0600, so `--cap-drop ALL` needs the uid to be the owner of the file *and* to have `x` on the directory; a `sudo install -d` directory with a file written by the unprivileged rename (or a one-sided `chown`) yields a container that cannot `stat` `keys.toml`, exits 1, and `--restart unless-stopped` loops it — the exact symptom ADR-0057 says this flag removes. Fix (in the repo's own style): refuse in `start_key` when `mount()`'s owner and `keys`' owner disagree, with a sentence naming both, because no flag can then be right; keep the flag's source as the file. Related nit: the `if let Ok(metadata)` else-branch silently drops the flag, and the sentence claiming `start_key` refuses first rests on `is_file()` and not on the same `metadata()` call.

**P2 · `crates/holosmith/tests/images.rs:603-621` `artifact()` — the candidate list is a fixed order with `x86_64` first, so the daemon-gated arm is wrong on an aarch64 host.** `scripts/build.sh` produces *both* musl artifacts into `dist/`, so on arm64 the first `is_file()` hit is the x86_64 binary; the manifest-list base then resolves to arm64 and `docker run … proxy egress --help` (`:744-760`) fails with an exec-format error — a red test for exactly the host-arch mistake this story's plan named (RESUME.md §1.5 item 7), and the production guard (`images::architecture`) is not in this path. Fix: try `env!("HOLOSMITH_TARGET")` first, then the other triple.

**P2 · spec axis (empty toolchain list) · `crates/holosmith/src/images.rs:146-150` `Expectation::value` — the read requires a label with an empty value, and nothing measures that the Dockerfile produces one.** `config/mod.rs:205-213` says an empty list is legitimate, but `value(LABEL_TOOLCHAINS)` returns `Some("")`, so `mismatches` demands `org.holosmith.toolchains == ""` to exist. If Docker drops an empty-valued `LABEL`, the empty-list machine rebuilds on every deploy *and* `doctor` fails it (`Check::Image` is the finding `serve` refuses on), with no test or case to say so: every build in the tree uses the default `["python3","ripgrep"]` (`verify.sh:5110`, `tests/doctor.rs:list-of-labels`). Fix: skip `LABEL_TOOLCHAINS` in `keys()`/`value()` when the expected list is empty, or build one image with `agent_toolchains = []` in `tests/images.rs`'s daemon arm and settle it.

**P2 · standards axis (a container that works by accident of its base's uid) · `verify.sh:5131` + `crates/holosmith/images/agent.Dockerfile:12-14` — "uid 1000, which is the host user's" is baked in as a fact and asserted as a constant.** 1000 is the *base's* uid. On a host whose user is 1000 by coincidence it is right; on a 1001 Linux user (or a macOS 501 dev machine) the session container writes the worktree as 1000 and the host user cannot commit to it — ADR-0035's concern — and the case cannot see it because it asserts `1000` rather than the invariant. Fix: assert `id -u` inside the image equals the invoking `id -u` (keeping the non-root guard), and reword the Dockerfile comment to "the base's `node`, uid 1000 — the uid this repository's Linux machines run as".

**Nits**
- `src/deploy.rs:1014-1024`: the `satisfied` sentence gives one clause to both images — "… carry this binary's labels: version …, git tag …, pi …, toolchains python3 ripgrep" — while the proxy image has no toolchain label. Split the clause.
- `src/images.rs:440`: `read` returns `Result<Status, String>` and every arm is `Ok`, so `deploy.rs:983-996`'s `Err(sentence) => return failed(…)` is a branch no test can reach. Return `Status`.
- `src/proxies.rs:214-232` `image_there`: `Containers::image_exists` is `succeeds()`-shaped (`docker.rs:92-97`), so a wedged or unreachable daemon produces "the image … is not on this machine … run `server deploy`'s step 3", untrue on that state (twice per boot). Add "or the daemon did not answer".
- `docs/build.md:347`: "runs **first among the cases that need the daemon**" is not true — `case_create_session`, `case_worktree`, `case_delete_keeps` and others precede it and need the daemon. The defensible claim is "first among the cases whose boot starts the proxies", which *is* true of the order.
- `src/deploy.rs` `Target`'s doc still lists "step 4's binary mount source" among the unprefixed machine facts; ADR-0057 removed that mount.
- `docs/build.md`'s `case_server_images` paragraph names the daemon and `python3` as prerequisites but not **outbound network** for the first build (`npm install` pi, `apt-get` toolchains) — `BUILD_TIMEOUT`'s own doc says so, so the gap is only in the case's prerequisite list.

### Verdict

**FIX-THEN-SHIP.** The story is implemented along its own design and the measurements are honest where they exist: the label read is the skip rule, the unlabelled doctor arm is reachable only through the real reader, the fourth label demonstrably changes a rebuild, the embedded consts (not copies) are what the daemon builds, and the new config key moved both places the repo's own recipe requires plus the automatic field↔row cross-check. What keeps it from a clean ship is one substantive hole and one untrue sentence in the same feature: the skip rule compares three strings and calls it "the binary", so a rebuilt artifact at the same `git describe` leaves both images running the previous build while the line says `satisfied` — and the ADR's justification for skipping a binary digest does not survive that case. Fix that (a digest label, or an honest ADR + landmine) and the staleness sentence in `images::failure`, close the gate's unverified "absent state" with the two lines `case_server_deploy` already has, and the P2s above are then ordinary follow-ups. Supervisor should run `cargo test`, then `scripts/verify.sh` (needs the daemon, `python3`, and network for the first build) and `scripts/check-static.sh` against a fresh `scripts/build.sh` artifact.
