## Standards

- **note (correct)** — The `Routes`/`App` seam is honoured exactly. `crates/holosmith/src/http/app.rs:323-327` registers the list through `Routes::get` with a comment saying why (`ReadOnly` in the manifest, guards with nothing added); `RouteKind::ReadOnly` is set by `Routes::get` itself (`app.rs:120`), so a mutating `GET` stays unexpressible. `tests/session_list.rs:176-194` pins `GET → ReadOnly` **and** `POST → Mutating` on the same path, and `tests/guards.rs:768-800` (`no_get_route_is_mutating`, `every_registered_route_is_classified`) now covers the new route automatically. `is_guard_exempt` (`app.rs:391`) is untouched, so the list sits behind the `Host` check and, when configured, the owner check (`guard.rs:73-110`) — the same as the stream.
- **note (correct)** — No lock across an `.await`: `list_locked` (`http/sessions.rs:308-323`) is a synchronous fn that takes the guard, calls `list(None)` and drops it before returning; the poisoned-lock handling is the repo's existing `unwrap_or_else(PoisonError::into_inner)` idiom, identical to `create_locked` (`sessions.rs:246-249`).
- **note (correct)** — ADR-0008's envelope on every error the list can produce: the single failure path is `internal("list", error)` (`sessions.rs:318`), i.e. the fixed 500 sentence, never a rusqlite message; guard refusals come from the one layer. `tests/session_list.rs:149-171` asserts 403 **and** `application/json` **and** `code == BAD_HOST`, not just the status.
- **note (correct)** — No `innerHTML` with server data. A grep of `web/src` finds no `innerHTML`/`outerHTML`/`insertAdjacentHTML`/`eval`; every write is `textContent` (`main.ts:79, 206, 212, 215, 273`) and every node is `createElement`. `frame.step` is interpolated into `textContent` (`main.ts:206`), which is safe.
- **note (correct)** — No new dependency. The diff touches no `Cargo.toml`, `Cargo.lock` or `web/package.json`; `crypto.randomUUID`, `EventSource` and `fetch` are the platform, and `web/tsconfig.json` (`lib: ["ES2022","DOM"]`, `strict`) covers them. `npm run build` is still `tsc --noEmit && vite build`.
- **note (correct)** — Retry semantics are implemented as ADR-0017 states, and the server side supports it: the key is generated at submit (`main.ts:316`), sent as `idempotency-key` (`main.ts:284`), cleared **only** after a 202 (`main.ts:301`), and kept on `!response.ok` (`main.ts:295-299`) *and* in the `catch` (`main.ts:304-305`), so a `fetch` that never answered keeps it. The server looks the key up before counting the cap (`sessions.rs:254-262`), so the lost-202 retry gets its own session instead of `cap_reached`.
- **should-fix** — `web/src/main.ts:316`: `pendingKey = pendingKey ?? crypto.randomUUID()` runs in the `submit` listener outside any `try` and outside the promise chain (`void submit(pendingKey)` on line 317), so a throw there is uncaught. `crypto.randomUUID` is secure-context-only — ADR-0017's own "Not decided here" bullet (`docs/adr/0017-…:105-109`) says the control listener is plain HTTP over the tailnet unless it is behind TLS. In that deployment the operator taps "Start session" and **nothing happens**: no row, no `unreachable` line, no disabled button, no console-free explanation. That is a silent dead form on exactly the device HS-013 exists for. *Fix:* wrap the call — `let key: string; try { key = crypto.randomUUID(); } catch { fail("unreachable", "this page needs a secure context to create a session"); return; }` — which surfaces the reason without adding a second key generator, so the recorded decision stands. (Whether a given phone lacks it is **unverified**; the secure-context requirement is stated in the ADR itself.)
- **nit** — `web/src/main.ts:53`: `LIVE_STATES: ReadonlySet<string>` while the set only ever holds `SessionState`; `ReadonlySet<SessionState>` would make `LIVE_STATES.has(state)` (`main.ts:158`) a check against the declared state set instead of accepting any string.
- **nit** — `web/src/main.ts:300-307`: `addSession` prepends unconditionally, keyed by nothing. A 202 whose body then fails `response.json()` leaves `pendingKey` set (line 301 is never reached), so the next press is answered with the same session and prepends a **second row** for one id — two rows, two `EventSource`s, frames applied twice. *Fix:* drop the row lookup into `addSession` (`list.querySelector('[data-session="…"]')`) or clear `pendingKey` before parsing. Contrived, hence a nit.

The boot config (`verify.sh:706`) does not set `network_default`, so `*'"network_default":false'*` is available and would catch a renamed or inverted field; likewise nothing pins the row's `"status":"starting"` or that `sessions` is an array. ## Spec

Each HS-013 acceptance bullet, judged against the code:

1. **"Lists id, project, model, state with reason, and last activity; live updates over the event stream."** — **Verified from source.** `sessionRow` (`main.ts:132-150`) renders `project`, `stateText(status, status_reason)` (`main.ts:100-102`, `state · reason`), `id`, `model` and `active <relativeTime(last_active_at)>` (`main.ts:107-122`); the list order is the server's (`repository.rs:45`, already covered by `tests/session_repository.rs:455-490`), and the page does not sort. Live updates: one `EventSource` per live row (`main.ts:155-196`) applying `session.status` frames (`state.rs:34`, `events/stream.rs:84-87`). **Unverified:** that frames actually arrive and repaint — needs a browser.
2. **"Form: project, model, thinking level, and an Internet access checkbox defaulting from `network_default` (off)."** — **Verified.** `main.ts:249-266` builds the three text fields and the checkbox, `network.checked = networkDefault`; `networkDefault` comes from the list body (`main.ts:340`, `sessions.rs:291-293,321`), whose value is `config.network_default`, defaulting `false` (`config/mod.rs:226`). The wire value is proven at socket level by `tests/session_list.rs:135-146`.
3. **"Create generates an `Idempotency-Key`, sends it, and shows `starting` immediately; a network failure and retry reuses the key."** — **Verified from source**, with the one caveat above. Key generated per submission, sent as `idempotency-key`, kept across both a refusal and a thrown `fetch`, dropped only on 202 (`main.ts:284, 295-305, 311-318`). `starting` is the 202's own row drawn straight from the body before the stream says anything (`main.ts:300-303`; the insert writes the table's `none` row, `repository.rs:26-29`, pinned by `tests/session_list.rs:96-131`). **Unverified:** the actual paint-before-first-frame and a real network failure/retry — browser + running binary.
4. **"Provisioning steps are shown while `starting`."** — **Verified from source.** A `from === to` frame sets `step.textContent = "<step>…"` (`main.ts:200-208`), and a transition clears it (`main.ts:214`); the step reports are the provisioner's (`state.rs:34`, `SessionStatus::step`). Order is safe because the stream replays in seq order and a transition is always after its steps, so a late step frame cannot resurrect a stale line.
5. **"Stopped sessions show days remaining before auto-delete (wired to HS-064; placeholder until then)."** — **Verified.** `retention` is an em dash with `title = "Days remaining until auto-delete arrives with HS-064"`, `hidden` unless `stopped` (`main.ts:143-146`), toggled on transition (`main.ts:213-216`). No number is fabricated, which is what the ADR asks.
6. **"Mobile-first layout: one column, tap targets sized for a phone."** — **Verified from source, arithmetic only.** `main { max-width: 32rem; margin: 0 auto }` (`style.css:12-15`) with `body { padding: 1rem }`, so at 320 px the column is 288 px and nothing is side-by-side: the list and the form are `flex-direction: column` (`style.css:47-52, 105-109`), `.session-meta` wraps (`style.css:88-94`), and long operator text breaks via `overflow-wrap: anywhere` (`style.css:71`). Tap targets: `button` and `.checkbox` are `min-height: 44px` (`style.css:130, 142`); `input[type="text"]` gets `font: inherit` (line-height 1.5 → 24 px content) + `0.625rem` vertical padding + 1 px border ≈ 46 px (`style.css:117-123`). **Unverified:** any of this rendered at 320 px — needs a browser.

Cross-cutting spec checks: item 7 step 3 ("return 202 with the session, the client opens the stream immediately") ✓ (`main.ts:300-303`); item 2's "default comes from `network_default`, which ships as off" ✓; item 8's six states spelled as the API spells them ✓ (`main.ts:21`); item 15's retention placeholder ✓. Out-of-scope things stayed out: no session screen or transcript (HS-014), no prompt/steer/abort, no resume/delete, no paging (HS-061), no router or framework, no second endpoint for the checkbox default. The API table has no row for `GET /api/sessions`; ADR-0017 records the endpoint, which is the same precedent HS-010 set for the stream endpoint — no action.

Live-update safety (the brief's explicit worry), from source: **cannot leak or miss within scope.** `syncStream` (`main.ts:155-172`) opens at most one source per row (`rowSources.set` happens synchronously in `openSource`, before any await, so no double-open), closes it on any non-live `to`, and is called both at draw time and after every frame, so exactly one source exists per live row. A dropped stream (`stream_lagged`, no `id`, `events/stream.rs:88-91`) ends the response, the browser reconnects with `Last-Event-ID`, and the replay fills the gap (`streams.rs:19-25, 68-81`) — so the page's "last frame wins, applied in arrival order" rule holds across a lag. The server-side registration is dropped when the connection ends (`events/registry.rs:109-131`), so `beforeunload` (`main.ts:389-395`) is a courtesy, not the thing that prevents a leak. A session that leaves a live state and later returns gets a source again, but nothing on this screen can trigger that (it is HS-018's resume), so no missed transition is reachable today.

## Summary

- Blockers: **none**.
- Should-fix: `web/src/main.ts:316` — `crypto.randomUUID()` is uncaught, so on a plain-HTTP tailnet page (a case ADR-0017 itself names) the Start button silently does nothing; wrap it and render the reason on the form's error line (no second key generator, so the recorded decision stands).
- Should-fix (nits worth doing in the same pass, no gate risk): `main.ts:300-307` dedupe by `data-session`; `verify.sh:594-628` assert `"network_default":false` and the row's `starting`; `main.ts:53` type `LIVE_STATES` as `ReadonlySet<SessionState>`; ADR-0017:127 reword the `Last-Event-ID` sentence; `web/index.html:14` refresh the `noscript` text; ADR-0017 record that list elements expose `client_key`.
- Merge verdict: **OK with notes** — the change is minimal, in scope, correctly guarded and read-only, the envelope and lock rules hold, no dependency arrived, `case_sessions_list` and the four socket tests exist (21 cases / 66 assertions confirmed by static count), and all six acceptance bullets are satisfied in source; only the uncaught `crypto.randomUUID` failure mode is worth a code change before release.
