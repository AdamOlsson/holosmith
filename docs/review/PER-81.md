**SPEC-1 (P1, Spec) — `perms` reads the *machine's* two paths, so a `--root` deploy's step 7 can fail on a tree it never wrote, and its sentence names a `chown` on the real install.**
`doctor.rs:514-515` builds the last two of the six paths from `deploy::ADMIN_DIR` and `config::DEFAULT_CONFIG_PATH` — absolute constants — while a `--root` deploy writes `<root>/run/holosmith` (`Target::admin_dir`, `deploy.rs:414-416`) and `<root>/etc/…`. `deploy.rs:1832`/`:1871` then call `doctor::run(config, Depth::Full, …)` in-process, so step 7 of a `--root` run compares the *host's* `/etc/holosmith/config.toml` and `/run/holosmith` against the *root's* data-root owner. On a host that has deployed for real (`~holosmith`-owned tree) a `--root` deploy therefore exits 1 at step 7 with ``…is owned by 987 where the data root's owner is 1000: chown 1000: /etc/holosmith/config.toml`` — a false verdict about the run, and an instruction to chown a file the run never wrote. It also makes the suite host-dependent in the direction `docs/notes.md:485-487` warns about: `tests/doctor.rs:302` pins the exact tally `doctor: 10 findings: 9 pass, 0 fail, 1 unknown` and `tests/deploy.rs:1027` asserts `!report.failed()`; both go red on a machine with a real install. *Fix:* thread the install target into `doctor::run` — doctor already imports `crate::deploy`, and `Target::{admin_dir, etc_config}` is the one spelling — so `perms` reads `<target>/run/…` and `<target>/etc/…`; the `doctor` command passes the machine target, `deploy::health` passes the run's. Add one `tests/doctor.rs` arm for the mixed machine. If that seal is too wide for this story, the honest stopgap is to make `perms` skip the two machine paths when they are not under `config.data_root` and record the limit in ADR-0058 D5 — but the failure sentence must never name a `chown` on a path the run did not write.

**STD-1 (P1, Standards) — the `keys.toml` mode-repair arm lost its only test; the assertions now check the fixture.**
`tests/deploy.rs:1023-1025` writes the key file at `0600` and the secrets directory at `0700`, then `:1034-1035` assert `mode(&keys) == 0o600` and `mode(&secrets) == 0o700`. Before this diff the fixture was `0644` and the assertion was *"the key file's mode was not repaired with chmod"*; the repair claim moved to the config file (`:1046-1056`), which exercises `Kind::Rendered`, not `Kind::Kept`. Mutation check: delete `wrong_mode.then(|| Action::Mode …)` from `Kind::Kept` (`deploy.rs:1014-1021`) and the suite stays green — the store's mode would never be repaired again, and nothing would say so. This is the rule `RESUME.md:968` states ("a test that cannot fail is worse than no test"), and it is the one leg of "ownership and modes are asserted" that now has no detector. *Fix:* restore the wrong-mode fixture (`0o644` on `keys.toml`, `0o755` on `secrets`) in that test and assert the plan carries `chmod 0600 <keys>` / `chmod 0700 <secrets>` while the bytes are unchanged — the pre-diff shape, which the new comment at `:1009-1012` still describes. Safe under `--root`, where step 1's `perms` does not read the root's tree, so the wrong mode reaches step 2.

**SPEC-2 (P2, Spec) — `perms` on `doctor --quick` makes step 2's `chmod` repairs unreachable on the system path.**
`deploy.rs:499-506` says every non-`ports` failure stops the run; `doctor.rs:227` puts `perms` in `--quick`; and the six paths it reads are five of step 2's seven items (only `/etc/holosmith`'s own mode escapes it). So on the system path a wrong mode anywhere in the install tree stops the deploy at **step 1**, and the `Action::Mode` repairs at `deploy.rs:1008-1021` are dead code — even though ADR-0056:94-98 still promises "a mode it does own is repaired with `chmod`". Reachable from our own programs: see STD-2. The operator recovers with one hand `chmod` (the sentence names it), so this is not a P1 — but the ADR records `perms`' *startup* consequence (D5) and not this one, and `docs/notes.md:1489-1494` explicitly forbids widening step 1's exception without an amendment. *Fix:* record the consequence in ADR-0058 D5 and the HS-049 landmines ("a wrong mode refuses the deploy at step 1 by design; step 2's repair arms are for a tree a `--root` run owns"), and pin it with a `tests/deploy.rs` arm asserting a wrong mode on the system path stops at step 1 with the `chmod` sentence (that arm also needs the SPEC-1 fix to be deterministic). Do **not** silently add `perms` to the `ports` downgrade.

**STD-2 (P2, Standards) — `serve` got the "a data root I created is 0755" rule; the key store did not.**
`commands/serve.rs:63-79` now sets `0755` on a data root it created, for exactly the reason `docs/notes.md:1640-1643` records. But `key::Store::ensure_file` (`key.rs:214-233`) and `save_unlocked` (`:246-252`) create the same directory with `create_dir_all` and then set only `secrets` to `0700` — so `holosmith key set <provider>` on a host that has not deployed leaves `/var/lib/holosmith` at `0775` (umask 0002), and the next `server deploy` refuses at step 1 (SPEC-2) while `doctor --quick` fails on a *mode* for a tree the operator asked for by running the documented next-step command. Three creators, one rule, two spellings. *Fix:* one helper (`data_root::ensure(path) -> Result<bool>`, "created ⇒ `0755`, existing ⇒ untouched") called by `serve`, `ensure_file` and `save_unlocked`, and let the deploy keep its `Action::Mode` repair as the reconciler.

### Verdict

The story is substantially done and, unusually, most of its hard claims are *measured* rather than asserted: the unit's bytes are compared byte-for-byte and read back with `is-enabled`, the VAPID pair's "never regenerated" is three facts with three tests, both origins are read from the real `serve status --json` shape, the health wait has both arms in milliseconds, `perms` is one check word with `unknown`/`fail`/`pass` and both values plus the fix in the sentence, and the gate's new `case_server_service` owns its state and fails if any of it is deleted. Two things should be fixed before this ships. **SPEC-1** is the real one: `perms` reads the machine's `/etc/holosmith/config.toml` and `/run/holosmith` no matter what the install target is, so a `--root` deploy's step 7 can fail on a tree it never wrote and hand the operator a `chown` on the real install — and it silently makes `tests/doctor.rs:302` and every step-7 test depend on whether the host has deployed. **STD-1** is the other: the `keys.toml` mode-repair arm lost its only detector, and the surviving assertions compare the fixture with itself. The four P2s are smaller but not optional-droppable in this repository, whose own notes make "a test that cannot fail" and "amend rather than rewrite" rules: the step-1/`perms` dead end needs recording (and `key::Store` needs the 0755 rule `serve` just got), and `ADR-0056:91`, `GLOSSARY.md:709`, `docs/notes.md:1496-1505` and `commands/deploy.rs:10` all now say things the code contradicts.

Test commands a supervisor must run (I did not run them, and they must be green on a clean tree with the artifact rebuilt): `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `cargo test --test schema_previous`, `cd web && npm test`, `cd web && npx tsc --noEmit`, `bash -n scripts/verify.sh`, then `scripts/verify.sh` — and the SPEC-1 fix should be verified by running one `--root` deploy on a host that also has a real install, which is the case nothing currently measures.
