## Standards

The change follows the repo's documented machinery well: one additive migration (ADR-0047), a status as text with a read-time refusal (ADR-0011), four codes in ADR-0008's table, the SQL-location guard built on the shared `sql::guard` rather than a second matcher, `force_requested` reused rather than re-spelled, and no new config key (`KNOWN_KEYS` and `tests/golden/config-default.toml` untouched; `hosts_seed` already existed). The guards apply to both mutating routes and `tests/guards.rs:768-808`'s generic classification covers the new ones. What follows are the places it drifts.

**T1 — major — Duplicated Code, and the copy has already drifted.**
`Origin::with_port` (`crates/holosmith/src/config/mod.rs:113-141`), `Origin::port` (`:143-163`) and `Origin::host` (`:165-179`) are three implementations of the same scheme/authority/bracketed-literal split — the comment "A bracketed IPv6 literal may itself contain colons, so only the brackets delimit it" appears twice verbatim — and `hosts::default_port` (`crates/holosmith/src/hosts/mod.rs:297-303`) is a fourth copy of the 80/443 table `config::default_port` already owns (`config/mod.rs:176`). They have already diverged: for the unterminated `http://[::1`, `with_port` fabricates `http://[::1:8080` (`config/mod.rs:126-128`) while `host()` returns `None` and `port()` returns `None`. And the new bracket branches are untested while the sibling's is tested (`config/mod.rs:1749-1750`), which is the one place a byte-index slice (`&authority[..literal.len() + 2]`, `config/mod.rs:169`) lives. This is the exact hazard `sql.rs:155-160` records ("Two copies of this matcher existed … and had already drifted"). Smallest fix: one private `split(&self) -> Option<(&str, &str, Option<u16>)>` with the three methods on top, and a bracketed case each in `the_local_row_is_the_one_that_names_this_machine` (`hosts/mod.rs:585`).

**T2 — major — the 3-second bound is not a bound, and two documents say it is.**
`probe.rs:39-44` says `PROBE_TIMEOUT` is "How long one probe may take — connect, request and answer included". In `plain` (`probe.rs:100-108`) the connect gets a full `PROBE_TIMEOUT`, the write gets another, and `let deadline = Instant::now() + PROBE_TIMEOUT` is computed *after* the write — so one `http` row can spend ~9 s, plus `resolve` (`probe.rs:242-251`), which the code admits is unbounded. ADR-0073 D9's "a boot pays up to `PROBE_TIMEOUT` per unreachable row before it serves" is therefore false. Two of the gate's own timeouts are smaller than the real worst case: `start_serve` waits 10 s for the banner (`scripts/verify.sh:10138-10143`) and `fetch` waits 10 s per request (`verify.sh:241`) — so a slow resolver shows up as `case_hosts/*_no_answer` or `serve/banner`, not as a slow case. Fix: one `deadline` at the top of `plain`, fed to `connect_timeout` and both `set_*_timeout`s via `saturating_duration_since`, and one sentence in the doc/ADR saying the resolver is the platform's and unbounded.

**T3 — minor — `merge`'s `now` parameter is dead.**
`hosts/mod.rs:408-412` takes `now` and writes it only into the pre-probe rows (`:447`), which the second loop immediately overwrites with `merge_outcome`'s `clock::unix_now()` (`:355-367`, `:464-476`). So `last_checked_at` in the table never comes from the caller, and the injected `1`, `2`, `3` in `tests/hosts.rs` and `tests/hosts.rs:…` `the_file_wins…` observe nothing. That is against the repo's own "the clock arrives as an argument" convention (`sessions::repository::create(now)`, `push`'s `created_at`). Fix: thread `now` through `merge_outcome`/`probe_row`, or delete the parameter.

**T4 — minor — the lock discipline is stated as fact and enforced by nothing (and the story's own tests break it).**
ADR-0073 D9: "parse, store (one lock scope), probe each row **with the lock dropped**". At that call site there is no lock to drop: `commands/serve.rs:215` calls the merge and the `Mutex` is only created at `serve.rs:309`, after the bind. `Database::hosts()`'s doc states the rule as a property (`db.rs:134-141`), and `merge(&Database, …)` cannot enforce it — a caller holding the guard passes it straight in, which is what `tests/hosts.rs` does: `hosts::merge(&database, …)` on a live `MutexGuard` across four probes including a TLS child (`the_probe_reads_a_real_answer…`, `the_file_wins…`, `the_local_row_is_refused…`). Nothing spans an `.await` in production — `http::hosts::register` awaits `spawn_blocking` *before* it takes the lock (`http/hosts.rs:92-110`), and `list`/`remove` take and drop theirs in a block with no await inside — so this is a documentation defect, not a deadlock. Fix: reword D9/`db.rs` to "call it before the `Mutex` exists, and never from a handler", and stop holding the guard in those three tests (drop it and re-acquire per call).

**T5 — minor — a sentence in the error column that is not an error.**
`hosts/mod.rs:446` writes `last_error: Some("not probed yet")` for every file row; the row is overwritten later in the same call, so the value is visible only to a process that dies between `:443` and the probe loop — and then a machine's `last_error` reads "not probed yet", which `Host`'s own doc says is `None` unless a probe failed (`hosts/mod.rs:120-128`). It also makes the first loop look like it records a status when its only real job is putting the file's URL in the table before it is probed. Fix: fold the two loops into one (write the row, probe it, write the measurement) or store the pre-probe row with the value the invariant allows and let the probe replace it.

**T6 — nit — `all.extend(stored)` + `seen` cannot contribute anything.**
`hosts/mod.rs:462-467`: every row in `stored` was `upsert`ed one statement earlier (`:443`), so the `all()` read at `:458` already contains it; every entry the `extend` adds is skipped by the dedupe. It reads as handling aliasing that cannot occur, and a future reader will assume the set is load-bearing. Drop the extend and the set, or drop the pre-write.

**T7 — nit — an unreachable match arm.** `RegisterError::Store` (`hosts/mod.rs:155`) is unconstructible: `hosts::register` answers `Result<Host, Refusal>` and `http/hosts.rs:92-95` maps every error to `Refused`, so `Ok(Err(RegisterError::Store(…)))` at `http/hosts.rs:99` is dead code. Fix: drop the arm and the variant, or let `register` own the store.

**T8 — nit — the new test helper contradicts the landmine the same commit records.**
`docs/notes.md`'s new entry says "A test stand-in must serve one connection and stop … One `accept()`, one answer, and the thread returns", and `probe.rs`'s `stand_in` does exactly that. `tests/hosts.rs:130-158` does not: it loops `for _ in 0..2`, so the thread blocks in `accept()` forever after the first probe, holding a bound port for the rest of the binary. Fix: stop after the second iteration (`break` when `counter == 2`, or drop the listener), or amend the landmine to say which shape is right where.

**T9 — nit — `probe` is coined as a term with no headword, and another entry _Avoids_ it.**
The **Reach** entry uses "the probe asks `GET /api/health`" (`GLOSSARY.md:67-73`), and `probe` is then a count noun through the ADR, `db.rs`, `hosts/mod.rs` and `docs/build.md`; the glossary has no headword for it, while **Self-test**'s `_Avoid_: Health check, smoke test, probe` (`GLOSSARY.md:682`) reserves the word for a different thing. Fix: give **Host probe** a headword (`hosts::{probe, PROBE_TIMEOUT, Outcome}`) with its own _Avoid_, or stop using "probe" for the registry.

All five have a check that can fail on its own arm. Three claims made about that coverage are not true of the code, and one acceptance arm is partially unmet:

**S1 — major — the port rule is skipped when the port does not parse, so bullet 1 is partly unmet.**
`hosts::port_problem` opens `let port = origin.port()?;` (`hosts/mod.rs:286`), and `Origin::port()` answers `None` for `:abc`, `:99999` and a bare trailing `:` (`config/mod.rs:158-162`). In a function returning `Option<String>` where `None` means "no problem", that `?` turns "not a port at all" into "allowed". So `POST /api/hosts {"url":"https://box.tail1234.ts.net:99999"}` passes `origin()` (`hosts/mod.rs:204-215`), the probe answers `Unreachable("… does not name a host and a port")` (`probe.rs:73-77`), and the route answers **201 with a stored row** that HS-069 can never forward to — instead of `422 bad_host_url`. No test covers any of the three spellings. Smallest fix: replace `:286` with `let Some(port) = origin.port() else { return Some(format!("`url`'s port is not a number: {origin:?}")) };`, and add `":abc"`, `":99999"` and `":"` to `the_port_is_unprivileged_or_the_schemes_own_default` (`hosts/mod.rs:553`) and to `case_hosts`'s `for pair in …` list.

**S2 — major — the gate says it asserts that the forced delete leaves the session alive; it does not.**
`scripts/verify.sh:5024` is the comment "The forced removal of the local row: the row goes, the session stays", and `docs/build.md:501-502` states the case asserts "its forced removal leaving the session". `verify.sh:5025-5032` asserts only that the row is `<absent>` and that the API-made row survived — the session is never read again, and the case never even extracts its id from `${name}_created`. This is the failure mode the brief names: an assertion that passes over nothing. (`tests/hosts.rs` *does* check it — `"the session outlived the row that named it"` — so the behaviour is proven; the gate paragraph is not.) Fix, three lines: `id="$(sed -n 's/.*"id":"\([a-f0-9]\{16\}\)".*/\1/p' <<<"$(answer "${name}_created")")"`, then after the forced delete `fetch "${name}_session" GET "/api/sessions/$id" "Host: 127.0.0.1"` and `expect_status "${name}_session" "$(answer "${name}_session")" 200`.

**S3 — minor — ADR-0073 D7's last sentence contradicts `probe_one`.**
D7 says "A row registered over the API for a tailnet origin *is* probed, including when it is this machine's own tailnet origin." It is not: `probe_one` shortcuts on `is_local`, not on which caller asked (`hosts/mod.rs:387-391`), so a `POST /api/hosts` naming this machine answers `201 reachable` with this build's version and no measurement — and the ADR never states that, which is the one row whose `reach` is a claim rather than a measurement. Fix: replace the sentence with what the code does (and say that a registration naming this machine is answered without a round trip, for D7's boot-order reason).

**S4 — minor — `merge`'s own doc and D9 promise a re-probe the early return prevents.**
`hosts/mod.rs:394` says the function reads the seed "and probe[s] every row in the table"; `:414-418` returns `Merge::default()` the moment `hosts_seed` is unset, so a machine with **no** seed probes nothing at boot — every API-registered row keeps whatever `reach`/`last_checked_at` it got at registration, forever, and a machine whose registry is only `POST /api/hosts` never re-checks anything. Item 16 does not require the re-probe, so this is a documentation/behaviour mismatch rather than an unmet bullet; but D9 sells the boot cost on the same promise, so one of the two must move. Fix: probe `database.hosts().all()` before the early return (the loop at `:464` already handles the file-less case unchanged), or reword both to "probe every row, when a seed is named" — and assert `merged.probed` in `tests/hosts.rs::a_seed_that_does_not_parse…`'s no-key arm so the chosen reading is pinned.

**S5 — minor — the distinct code from bullet 2 is never observed as an answer, and its status is asserted nowhere.**
ADR-0073 D10's split is honest about *why* (`not_holosmith` needs a live listener the API will accept, and the predicate refuses loopback), and each link does have a failing test: `interpret` (bytes → `Refused`), `accept` (outcome → `Refusal::NotHolosmith`), `refusal_of` (refusal → code). What no test covers is the composition, and `ApiError::not_holosmith`'s **status** is asserted by nothing — `http/hosts.rs:250-262` compares `body.code` only, so changing `StatusCode::UNPROCESSABLE_ENTITY` to `200 OK` on that one constructor leaves the suite green while the API no longer refuses. Fix: assert `error.status` next to `error.body.code` in `each_refusal_is_its_own_code` (the three 422s and `host_busy`'s 409), and add one test that runs the real probe into the mapping — `hosts::accept(hosts::probe::ask(&loopback_origin, &Tools::default()), "workshop", &origin)` against the existing `stand_in(answered(foreign))` — which reaches `not_holosmith` through `interpret`, not through a literal string.

**S6 — minor — under `--port 0` the local-row shortcut can never fire, so a healthy machine's own row is born `unreachable`.**
`apply_overrides` sets `control_origin` to `…:0` (`config/mod.rs:366-370`) at `serve.rs:52`, long before the merge at `serve.rs:215`; `serve` fixes the origin only after `bind` (`serve.rs:273-275`). So on a `--port 0` boot — `start_serve`'s own default, and every dev boot — `is_local` compares against port `0`, a `hosts.toml` row naming this machine is *probed*, and the merge runs before the listener serves, so the row is born `unreachable` on a perfectly healthy machine. That is precisely the failure ADR D7's "a local row is not probed" exists to prevent, and the reason the gate had to grow `start_serve`'s third argument (`docs/notes.md`, `verify.sh:10124`) — the workaround is documented, the behaviour is not, and nothing tests it. Fix: either state it in D7 as a `--port 0` limitation, or set `control_origin` to the bound port before the merge (move the merge inside the async body, after `bind`).

## Correct (evidence, so the fixes above are not read as a rewrite)

- **The probe's shape is right for the two failure modes this repo has hit.** `tls` waits with `try_wait` against a deadline and only then reads (`probe.rs:184-215`), so an `s_client` that goes quiet on stdout cannot hang the thread; the redirect is a refusal in one place (`interpret`, `probe.rs:262-268`) and `case_hosts` proves it as a client can see it — `check "$name/redirect/asked" 1 "$(grep -c '^redirect$' "$log" || true)"`, which fails on `0` because `check` compares strings and `grep -c` prints `0` even when it exits 1.
- **The gate's needles are non-vacuous.** `hosts_row_field` prints `<absent>` for a missing row, so `check … reachable "<absent>"` fails rather than passing; `list/rows 5` and `merge/rows 5` fail on an empty list (`0 ≠ 5`); `self/version` compares against `$version` from `artifact version --json`, so a probed (or `null`) local row fails.
- **The gate owns its state and gives it back**: `extra_pid` is registered for the trap (`verify.sh:4885`, matching `case_push`'s idiom), the stand-in is killed and waited, the tree is removed, and the shared boot is restored with `stop_serve; start_serve` — which also restores the `port`/`control_origin` globals the next case reads.
- **All-or-nothing is real**: `seed::parse` runs to completion before the first `upsert` (`hosts/mod.rs:426-443`), so a malformed file writes nothing — and `tests/hosts.rs::a_seed_that_does_not_parse…` asserts the untouched row *and* the sentence naming the file.
- **`Answer`'s fourth field moved nothing**: every payload fixture already spelled `"name"` (`tests/deploy.rs:247`, `tests/doctor.rs:377`, `src/doctor.rs:1159`, `src/http/health.rs:188`, `verify.sh:8144`), and no machine's payload becomes refused, because `Health` has always shipped `name` (`health.rs:40,52`).
- **The SQL-location guard is the shared one** (`Guard::new("hosts", "hosts/repository.rs", …)`, `hosts/repository.rs:196-198`), the walk covers all of `src/**` so nothing can hide in `hosts/mod.rs` or `hosts/seed.rs`, and the test proves the walk read the crate (`sources.len() > 40`) and fires on a planted statement (`["planted.rs:1: from hosts"]`) while `hosts_notes` does not.
- **The migration moved everything it had to**: `SCHEMA_VERSION` 6, and all three vectors in `tests/db_migrations.rs` (`:144-145`, `:166-167`, `:357-358`); `tests/schema_previous.rs` only refuses a *missing* table/column (`:133-148`), so an added table needs nothing and `docs/schema/previous.sql` correctly stays for the release step.
- **The `409`'s sentence is true of what the code did**: `remove` reads the row, counts, and removes nothing before the refusal (`http/hosts.rs:127-155`), and "removing the row does not stop it" is the behaviour `tests/hosts.rs` proves after `?force=true`.
- **`is_local` cannot confuse two machines for one**: after `with_port` folds both sides, equality means same scheme + same host text + same port. It *can* answer no for one machine spelt two ways (`localhost:8080` vs `127.0.0.1:8080`, or an IP vs its MagicDNS name) — an inherent limit that D7 states as "its origin equals this machine's `control_origin`", and the unit test pins the positive and five negatives (`hosts/mod.rs:585-621`).

## The brief's questions, answered

- **A check that can fail per bullet** — table above. The one boundary-only arm is bullet 2's `422 not_holosmith`; the split is honest about the probe but *incomplete* about the mapping's status (S5), and two claims of measurement are simply untrue (S2, S3).
- **Does `probe` block on something unbounded?** Yes, twice: `to_socket_addrs` (`probe.rs:242-251`) and, for `https`, the child's own resolution; and `PROBE_TIMEOUT` is per-step, not per-probe (T2). A *dribbling* peer cannot extend it — the read deadline is absolute and recomputed from the same `Instant` (`probe.rs:108-135`) — but the deadline starts after connect and write.
- **Lock discipline** — right where it matters (`spawn_blocking` before the lock, no guard across an await or a socket in any handler), wrong where it is asserted as a guarantee: there is no lock at the merge's call site, `merge(&Database)` does not prevent one, and the story's own tests hold one across four probes (T4).
- **Is `is_local` right?** Two machines cannot compare equal; one machine can compare unequal to itself when spelt differently (documented limit); a non-origin deserialised `control_origin` yields `None` on both `host()`/`port()` and answers `false` rather than panicking (safe). The real defect near it is the `--port 0` case (S6).
- **The seed's asymmetry** (D6) — defensible, and *not* exploited: `case_hosts` step 2 measures the API's URL rule directly with six refusals, so the loopback seed row buys the probe's success path, not silence about the predicate. The one thing it hides is bullet 2's answer-side, which the ADR admits.
- **The delete's refusal** — the honest reading of "while it has live sessions" for a build that owns one machine's rows, and the `409`'s sentence is true of what the code did.
- **Migrations** — nothing else moved that should not have: `SCHEMA_VERSION`, the three `db_migrations` vectors, the additive rule, `db.rs`'s reader (`Database::hosts()`, `db.rs:134-141`), and `HostRepository::new` kept `pub(crate)`.
- **The SQL-location guard** — same shape as `push`/`events`/`sessions` (`Guard::new` + shared `sources_under`/`names_word`), and no statement can hide outside `hosts/repository.rs`: the walk reads every file under `src/`. (The `STATEMENTS` list does not cover `REPLACE INTO hosts`, but neither does any sibling's — pre-existing, not this story's.)
- **The error table** — each code is the client's next step and the statuses are right (422 for three field facts, 409 for `host_busy`); the messages are the caller's and each names its own request; `bad_host_body` avoided the trap ADR-0008 warns about by saying "a `name` and a `url` string" rather than reusing a create's sentence. The gap is that one status is unasserted (S5).
- **Does the gate measure the artifact?** Yes for the seed, the probe's three outcomes, the redirect's one request, the API's six URL refusals and two name refusals, the local row's `409`/force, and both halves of "the file wins". It over-claims one assertion (S2), its `nameless` needle is weak (`*name*` is satisfied by any sentence containing those four letters), and it inherits the resolver's lack of a bound (T2).
- **`Answer`'s fourth field** — every fixture already moved; no payload is newly refused.
- **`docs/`** — the ADR index line describes the ADR it points at; `docs/build.md`'s paragraph is true of the case except for the session-stays clause (S2); the glossary's **Reach** entry has no synonym problem but the word *probe* it introduces has no headword and is another entry's _Avoid_ (T9).

## Merge verdict

- **Standards: OK with notes** — 2 major (T1 duplicated/drifting `Origin` parsing, T2 a false bound), 3 minor, 4 nit. Nothing here is a behaviour defect in production paths today.
- **Spec: BLOCK** — S1 is an acceptance arm genuinely unmet (a port in no range is accepted and stored as a successful row), and S2 is a gate claim that asserts nothing, which is the exact failure this repository asks a reviewer to catch. Both are small fixes (a `?`→`else` in `port_problem`, three lines in `case_hosts`); S3–S6 should ride along.
- Totals: 9 Standards findings, 6 Spec findings, 0 blockers. Worst per axis: T1 (duplicated, already-diverged parsing of the origin both rules depend on) and S1 (an accepted URL the registry can never use).

Test commands a supervisor must run (I did not run them): `cargo test -p holosmith --lib hosts`, `cargo test -p holosmith --test hosts --test db_migrations --test schema_previous`, and `bash scripts/verify.sh` (the `case_hosts` arm needs `python3` and `openssl`; without them the case prints one `SKIP` line and the five acceptance bullets lose their only end-to-end check).
