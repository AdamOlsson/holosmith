## Standards

1. **P2 — `touches_ci` applies the directory-prefix arm to file-name entries, so backup copies of CI files count as CI.** `crates/holosmith/src/changes.rs:542-550`: `CI_PATHS.iter().any(|entry| path.starts_with(entry) || name == *entry)` applies *both* arms to *every* entry. For a file-name entry, `path.starts_with(entry)` is a prefix match on the whole path, so a root-level `Jenkinsfile.old`, `Jenkinsfile.rs`, `.gitlab-ci.yml.bak` or `codecov.yml.orig` all answer `touches_ci: true` (for `Jenkinsfile.old`: `name == "Jenkinsfile"` is false, but `"Jenkinsfile.old".starts_with("Jenkinsfile")` is true). **This is a defect**, in the safe direction only (a spurious "this touches CI" warning before publish, never a missed one), and it cannot be seen from the tests: `tests/changes.rs:360-376` uses `src/Jenkinsfile.rs`, where the *path* does not start at the entry and the name arm correctly fails, so the test reports "a look-alike cannot answer yes" while a root-level look-alike does. The directory arm is dead for the reverse reason (`name` never contains `/`, so `name == ".github/"` is unreachable — harmless but a sign the two arms were meant to be exclusive). **Smallest fix:** branch on the entry's own spelling — `if entry.ends_with('/') { path.starts_with(entry) } else { name == *entry }`. Nothing is lost: `name == entry` already covers a root-level `Jenkinsfile` (its last segment *is* `Jenkinsfile`), and this makes the sentence at `changes.rs:62-65`, ADR-0061 D8 and `GLOSSARY.md:550` ("file names matched on the last path segment") true as written.

2. **P3 — the docs describe name-only matching while the code prefix-matches, in three places.** `crates/holosmith/src/changes.rs:62-65` ("a **file name** (matched against the last segment of a changed path)"), `docs/adr/0061-...md` D8 ("file names matched against the last segment"), `GLOSSARY.md:550` ("file names matched on the last path segment"). The code (finding 1) does both arms for name entries. Fix: finding 1's code change (preferred — the docs then match) or, if the over-match is deliberate, say so in all three places.

3. **P3 — `mergeable`'s argument order is not pinned by any test.** `crates/holosmith/src/changes.rs:464-471` runs `merge-tree --write-tree <target_ref> <branch_ref>`, and the doc says the order is the merge's. The only conflict fixture (`tests/changes.rs:379-420`) is *symmetric* — both sides add the same new path from a base that lacks it — so swapping `target_ref` and `branch_ref` would keep every assertion green, including `Some(false)` and the reason naming `f.txt`. Contrast `DIFF_FLAGS`, which *is* pinned (`changes.rs` `the_diff_reads_ask_for_the_command_and_not_the_repository_s_config`) and the diff argument list, which is pinned by `the_diff_reads_end_with_the_two_commits_it_names`. Fix: one test in the spirit of the latter, asserting `merge_trial`'s argument vector is `["merge-tree", "--write-tree", "refs/heads/main", "refs/heads/agent/<id>"]`, or an order-sensitive fixture (base has `f.txt`; branch deletes it, target modifies it).

4. **P3 — `behind` re-spells ahead's count-and-parse.** `crates/holosmith/src/changes.rs:440-459` re-implements what `Worktree::ahead` does in the other direction, including the hand-built `GitError { command: git_command(..), detail: format!("git printed {text:?}, which is not a count") }`. ADR-0061 D1 records the deliberate choice that `worktree.rs` gains visibility and no behaviour, so this is not a violation — but the ten lines are a second spelling of "run `rev-list --count`, parse, refuse a non-number". Report-only; if `worktree.rs` ever grows a `count_between(&self, range)` helper, both should move.

5. **P3 — ADR-0061 does not record the decision the handler actually depends on.** `crates/holosmith/src/http/changes.rs:78` builds the worktree from the naming rule (`Worktree::of(projects_root, project, id)`) and deliberately ignores the row's recorded `session.worktree`; the reasoning lives only in the handler's module doc (`http/changes.rs:22-26`). The ADR's own prose ("the row already carries `worktree` and `base_commit`") points a reader at the other choice, and D1/D3 never mention it — a decision "a later reader could take a different way", which is the ADR's stated bar. Fix: one sentence in D1 or D3.

6. **P3 — the glossary says the changes view "writes nothing"; the ADR says otherwise.** `GLOSSARY.md:534` ("It is a **host** read (never a container), it writes nothing") against ADR-0061 D10 ("`merge-tree --write-tree` *does* write unreferenced tree objects into the repository's object store") and `changes.rs:464` (the command is used precisely because it writes a tree). Fix: "writes no ref and no working tree".

7. **No findings — reachable panics (Q7).** There is no `unwrap`/`expect`/indexing on a request path. `changes.rs` uses `unwrap_or(path)` for the last segment (`:544`), `let-else`/`?` in `conflict_paths` (`:487-500`), `Option` returns in `parse_numstat`/`count` (`:335-360`), `unwrap_or((None, None))` in the join (`:301-320`), and `map_err` on every count parse (`:440-459`); `http/changes.rs:61-64` recovers poisoning with `unwrap_or_else(PoisonError::into_inner)` and handles the `spawn_blocking` `JoinError` (`:86-87`). `String::from_utf8_lossy` is used everywhere git's bytes become text.

8. **No findings — lock scope and async placement (Q5).** `http/changes.rs:60-66` opens the database lock in a block, calls the synchronous `sessions().get(id)`, and closes the block; the only `.await` (`:80-81`) is after the guard is dropped, and `targets`/`worktree` are cloned/moved into the closure beforehand. The five git spawns all run inside `spawn_blocking`, so no runtime worker parks on a subprocess.

9. **No findings — re-spelling (Q6).** `changes.rs` never formats `agent/<id>`: it uses `worktree.branch` verbatim, reuses `Worktree::ahead` for the ahead count, `registered()`/`branch_head()` for state, and the `worktree.rs` git runner (`git_output`, `git_command`, `git_error`) rather than `Command::new("git")`. It does spell `refs/heads/{...}` locally in three places (`:424`, `:441`, `:465`) for fully-qualified refs; that is local qualification, not a second definition of the branch name (see finding 4 for the one genuine echo).

## Spec

1. **P2 — the 409 mapping for two of the four `ChangesError` arms is unmeasured, so acceptance bullet 6 is only half-proven.** `http/changes.rs:99-102` maps `NoRepository`/`Missing`/`Unregistered`/`NoBranch` to `409 no_worktree` and `Git` to 500. `tests/changes.rs` proves the *wire* for `Missing` (`:665-681`, 409) and `Git` (`:683-695`, 500), and the no-`base_commit` 409 (`:622-663`); for `Unregistered` (`:475-497`), `NoBranch` (`:511-544`) and `NoRepository` (`:499-509`) it asserts only that `Changes::read` returns the variant. Mutating `refusal()` to answer `Unregistered`, `NoBranch` or `NoRepository` with `internal(..)` (i.e. a 500) leaves `tests/changes.rs` entirely green; only `scripts/verify.sh`'s `case_changes` catches the pruned case (the `_pruned` 409), and nothing at any level catches `NoBranch`/`NoRepository` going 500. Fix: two more wire tests copying the shape of `:665` — the `NoBranch` fixture already exists in `:511`, and `NoRepository` needs only `std::fs::remove_dir_all(&fixture.repo)` before `served()` (its row still has a `base_commit`, so the handler does reach `Changes::read`).

2. **P3 — `mergeable: null` and `target: null` never appear in a test at the HTTP boundary, so the acceptance's "a client can distinguish `null` from `false`" is measured only in Rust.** The distinction is real in the code: `mergeable: Option<bool>` with a plain `derive(Serialize)` and no `skip_serializing_if` (`changes.rs:104-140`) serializes `None` as JSON `null`, and `mergeable_reason` is always `Some` in the `None` case (`:213-226`). But `tests/changes.rs:572-608` only sees `Bool(true)`/`Null` (the reason), and the no-target cases (`:422-451`) are `Changes::read` calls. A mutation adding `#[serde(skip_serializing_if = "Option::is_none")]` — dropping the key for a client that then cannot tell "could not ask" from "absent" — would keep every test green (the no-`base_commit` 409 test is not JSON-shape sensitive). Fix: one wire test over a repository whose `[merge] targets` names a branch that is not there, asserting `body["target"] == Value::Null`, `body["mergeable"] == Value::Null` and that `mergeable_reason` is a string.

3. **P3 — the "host git, no container" bullet cannot fail as a test, and `tests/changes.rs:622` claims it does.** The bullet is enforced by the type signature (`Changes::read(&Worktree, &str, &[String])` — there is no backend to ask), which is stronger than a test but is a compile-time property, not a measurement. The comment ("which is also the measurement for 'no container is involved'") overstates: that test asserts the 409 from a missing `base_commit` and would pass unchanged if some other route asked a container for the summary. Fix: either reword the comment to say the guarantee is structural, or note in the test module doc that the fixture has no Docker socket and the module cannot name a backend. Report-only for the bullet itself — nothing is wrong with the implementation.

4. **P3 — `NoRepository` as a 409 sits against ADR-0061 D7's own rule.** D7 says "a state of the session is a refusal, a machine problem is not (ADR-0030's reasoning, applied to a read)", and a project checkout that has gone away is not a state of the session — the sentence at `http/changes.rs:50-52` is an operator instruction ("restore the project's checkout under the projects root"), which is the shape of a 500's audience. It is *defensible*: creating/resuming a session over the same condition is a 4xx project refusal (`Refused project`, `GLOSSARY.md:485`; `gt_not_directory`/`submodules_present`/`worktree_config_enabled`), so a read that inherits the checkout's state says 4xx too. But D7 does not cite that precedent, so the table reads as an exception to its own rule. Fix: one clause in D7 naming the create's project refusals as the precedent (no code change).

5. **No findings on the remaining bullets.** Bullet 1 (eleven keys) fails if a field goes: `tests/changes.rs:572-608`. Bullet 2 (`behind` counts what the target has) fails on a swapped range because the fixture is deliberately asymmetric — `ahead == 2`, `behind == Some(1)`, plus `assert_ne!(changes.behind, Some(changes.ahead))` (`:201-249`), and `verify.sh`'s `case_changes` repeats the asymmetry with an explicit `counts_differ` check ("2 1"). Bullet 3 (merge-tree, no working tree touched) fails if the read merged for real: `:379-420` snapshots the repository's HEAD, the repository's `status --porcelain` and the worktree's `status --porcelain` before the read, plants an uncommitted file first, and compares after. Bullet 4 (`dirty` from the session's worktree) fails if the wrong directory is read (`:268-291` — the untracked file lives in the worktree while the repository is clean; `:293-309` pins `--untracked-files=normal` against `status.showUntrackedFiles = no`). Bullet 6's *ordering* — a pruned worktree whose directory exists caught before any git runs inside it — is correct: `changes.rs:163-200` checks `repository.is_dir()`, then `worktree.path.is_dir()`, then `worktree.registered()` (a `worktree list` in the *repository*), and only then `branch_head`/`ahead`/diff/status inside the directory, so the `Unregistered` refusal wins over git's "not a git repository" (`tests/changes.rs:475-497` and the gate's `_pruned` case agree). The nulls are answers rather than accidents: `target`/`behind`/`mergeable` are `Option`s whose `None` is always accompanied by a sentence (`changes.rs:213-226`, `no_target_sentence`, `conflict_sentence`'s empty-paths fallback), and binary counts are `None` rather than `0` (`:335-360`, tested at `:311-328`). ADR-0061 otherwise matches the code on D2 (two-dot), D3 (`branch_head`), D4 (first existing target), D5 (`--no-optional-locks`, `--untracked-files=normal`), D6 (three arms + additive `mergeable_reason`), D7's sentence table (all five constants match verbatim), D8's 16-entry `CI_PATHS` (7 prefixes + 9 names, exact), D9 (flags, `spawn_blocking`, binary nulls), D10 (no start lock) and D11 (the asymmetric test), and the glossary matches on **Behind**, **Mergeability** and **Target branch** — the only drifts are findings 1/2 (`touches_ci`) and 6 (Standard).

**Merge verdict: OK with notes** — the acceptance is implemented and bullet-tested apart from the two coverage gaps in Spec findings 1 and 2; the `touches_ci` over-match (Standards finding 1) is the one behavioural defect and is a two-line fix. Tests to run for this review: `cargo test --test changes`, plus `scripts/verify.sh`'s `case_changes` (the only place the pruned-worktree 409 is measured end to end).
