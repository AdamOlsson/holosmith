## Standards

1. **P1 — a `server` is offered peers it cannot reach, in two places.** `web/src/transcript.ts:1300-1307` (`createTargets`) filters registry rows on `reach` only, and `web/src/main.ts:2383-2386` (`settingsSection`'s `machines`) adds every non-local row the same way. The repo's rule is `forwards(role)` (`transcript.ts:774-776`), and `forwardingNote` (`transcript.ts:1245-1252`) states it in the same file, for this exact screen: "A `server` still keeps a registry — the seed is copied to every machine so the lists stay aligned — but the forwarding route exists only where a machine forwards (ADR-0074), so a hop out of a `server` is its own `404 not_found` … instead of offering a control whose only answer is a refusal". Consequence on any `server` with a seeded registry (i.e. every deployed one): the create picker offers `workshop`, whose `POST /api/hosts/workshop/sessions` is that machine's own `404`; and the settings screen's `workshop` row reads **"workshop · away"** with a `not_found: …` sentence (`gather`, `main.ts:2512-2516`) — a false claim about a machine that is up. The new test enshrines it (`web/test/transcript.test.ts:1697-1701` expects `["local","workshop","build-box"]` from `createTargets("server", rows)`). **Fix:** `const reachable = forwards(role) ? rows.filter((row) => row.reach === "reachable") : []` in `createTargets`, and `forwards(role) ? hosts.filter(...) : []` for the settings rows; add one arm to each test. `createTargets` already takes `role`, so the data is there.

2. **P1 — three comments and the ADR claim `hostFailure` drops the two upstream codes. It does not.** `web/src/main.ts:2185-2187` ("`hostFailure` drops the code of the two upstream words, because `upstream_unreachable: workshop could not be reached` reads as a word to look up"), `:2215` (the call), `:2511` and `:2516`; ADR-0079 D4/D5 repeat it. `HOST_REFUSALS` is `["bad_host_name","bad_host_url","not_holosmith"]` (`transcript.ts:1232-1236`), so `hostFailure("upstream_unreachable", m)` returns `"upstream_unreachable: m"` — precisely the string the comment says it avoids, drawn on the away session page and in the settings row's sentence. HS-071's actual rule is one screen over: `fillGroup` (`main.ts:470-481`) uses `answer.message` alone, "not through `hostFailure`". Nothing catches it because the web fixture is a value the code cannot produce (`web/test/push.test.ts:236`: `away: "workshop could not be reached"`). **Fix:** one predicate beside `hostFailure` — `awaySentence(code, message)` over `["upstream_unreachable","upstream_timeout"]` — used at both sites, with a unit test; then correct the two comments and ADR-0079 D4/D5.

3. **P2 — `docs/build.md` has no "…and since HS-074" paragraph.** The standard is `docs/notes.md:662-664`: "**`docs/build.md` is a story deliverable, not orchestrator-only.** If a story changes prerequisites or gates, the doc is in scope, and its prose must be reflowed (~100 columns)". Every story from HS-047 (build.md:594) to HS-073 (build.md:568-592) has one; this diff touches GLOSSARY, notes, the ADR index and `verify.sh`, but not build.md. This is also where the case's three tool `SKIP`s and the part no gate can see (the picker, the away screen, the settings rows — all `main.ts`) would be disclosed. **Fix:** one reflowed paragraph after `build.md:592`.

4. **P2 — the ADR index count did not move.** `docs/stories/README.md:117` still says "Seventy-eight decisions…" while the diff adds the ninetieth-line bullet for ADR-0079 (`README.md:203`); `docs/adr/` now holds 79 files. `RESUME.md:1358` and PER-105's review (`docs/review/PER-105.md:22`, "the count moved 77→78") both treat the count as part of that edit. **Fix:** "Seventy-nine".

5. **P2 — the settings row's state machine is a rule living in the untested file.** `web/src/main.ts:2417-2432`: a four-branch cascade from `PushAction` to the row's word (`"subscribed"`/`"not-subscribed"`/`"away"`/`null`→`"not-subscribed"`). `MachineSubscription` is declared in `push.ts:288`, so the mapping belongs beside `pushState`; today any mistake in it is unmeasurable (question 5). **Fix:** `export function machineSubscription(action: PushAction): MachineSubscription | null` in `push.ts` + a test over all six actions.

6. **P2 — a settings row claims "not subscribed" before any machine has answered.** `main.ts:2429`: at the first `draw()` every `row.decided` is `null`, so `state ?? "not-subscribed"` renders **"workshop · not subscribed"** beside `GROUP_WAITING`'s "reading…" (`transcript.ts:1269`). The comment at `main.ts:2650-2652` claims the opposite ("The first draw is `reading…` on every row… so no control is offered on a guess") — the control is withheld, the word is not. This is the `false`-is-a-claim rule (HS-071, `COUNTS_UNKNOWN`) two screens on. **Fix:** `row.name.textContent = decided === null ? hostLabel(row.host) : machineState(...)`, or a fourth `MachineSubscription` word for "not read yet".

7. **P3 — "away" is an invented word, and one screen spells it "unreachable".** GLOSSARY's **Reach** (`GLOSSARY.md:125-131`) already owns this fact with `reachable`/`unreachable` and `_Avoid_: … online`; the diff adds `MachineSubscription = … | "away"` (`push.ts:288`), `pushActionLabel("away") → "Away"`, and "away" as prose in ADR D3/D5 and the notes, with no GLOSSARY entry — while `awayScreen` puts the reach word **"unreachable"** into the session's `.state` span (`main.ts:2210`), the slot `stateText` (`transcript.ts:529`) fills with a *session* state. **Fix:** either define **Away** (and say how it differs from **Reach**, which is as old as the boot's probe) or reuse Reach's word in the row; and give the machine its own class rather than the session's `.state`.

8. **P3 — two sentences still say the payload has six keys.** `scripts/verify.sh:1455-1457` (the gate's own comment on the endpoint this story changed): "The health payload: exactly six keys (the sixth is HS-067's application server key)". 9. **P3 — the case's header sentence overstates its own fixture.** `scripts/verify.sh:6092-6093`: "with two endpoints — a different push service subscription per machine, because each machine's pair mints its own" — but the case sends **one** `p256dh`/`auth` pair (`$subscription_public`, `$auth_b64`) to both subscribes (6275-6300), whereas a second `PushManager.subscribe` mints a second key. What it measures (two rows, two tables, the peer's pair on the wire) is unaffected. **Fix:** "two endpoints and one browser key".

## Spec

1. **P0 — the tap cannot open another machine's session: the worker never writes `host` into the notification's `data`.** `web/src/sw.ts:115-116` reads `readTarget(click.notification.data)` and builds `notificationPath(target.host, target.sessionId)`; `readTarget` (`sw.ts:176-186`) looks for `data.host`. But the `push` handler still stores `data: { session_id: payload.sessionId }` (`web/src/sw.ts:103`). So `host` is always `""`, and `notificationPath("", id)` is `/sessions/<id>` (`push.ts:96-105`) — *this* machine's path. On the hub that URL loads the shell, whose `GET /api/sessions/<id>` is the hub's own and holds no such row, so the operator lands on `not_found: …`. Acceptance bullet 2 ("Notification payload `{host, session_id, kind}` opens the right machine's session through the hub"), the demo, and item 11's "Tapping opens that session" all fail; ADR-0079 D3 asserts the change that was not made ("The worker keeps its three events and **gains the host in the notification's `data`**, because `notificationclick` runs on the hub's origin and has no page to ask which machine an id belongs to"). Nothing catches it: `readTarget` is in `sw.ts` (no `npm test`), `push.test.ts` only tests `notificationPath` directly (`web/test/push.test.ts:114-171`), and `case_pwa`'s needles (`verify.sh:4764-4774`) do not include the data shape. **Fix (one line + one seam):** `data: { host: payload.host, session_id: payload.sessionId }`, and put that object behind `notificationData(payload)` in `push.ts` so `push.test.ts` can assert the two keys travel together (a needle in `case_pwa` is optional; a tested rule is better).

2. **P1 — `/api/health`'s seventh key has no reader, and four places say it has two.** The page's `Health` type does not declare it (`web/src/main.ts:114-121`); grep finds **no** `machine_name` anywhere under `web/`; in Rust the only reader is `push::announce` reading it from the *config* (`push/mod.rs:366`), and `http::health::Answer` deliberately does not (`health.rs:89-96`). Yet `health.rs:39-44` says the key exists "so a page can label its own row with the name the phone will show and a hub can read a peer's claim through the hop", `config/mod.rs:248-251` repeats it, ADR-0079 D1 repeats it, and `GLOSSARY.md:13-19` states it as fact — three paragraphs under health.rs's own rule: "a key nobody reads is a promise about a shape". The visible consequence: with `machine_name = "workshop"`, the phone shows `Holosmith · workshop` while the app's own row says **`local · this machine`** (`main.ts:2429` → `hostLabel`, `transcript.ts:1241`), so no screen shows the configured name and the operator cannot check the one string the tap depends on. **Fix:** declare `machine_name` on the page's `Health` and label the local row (settings + the picker's first option) with it — the promise then holds; or delete the page-consumer clause from ADR D1, health.rs:39-44, config/mod.rs:248-251 and GLOSSARY.md:16-18. Either way the sentence must match the code.

3. **P1 — acceptance bullet 1's app half is measured by nothing.** "The app subscribes per machine it uses through the hub" is implemented only in `main.ts:2479-2550` (`subscriptionFor`'s `getSubscription({applicationServerKey})` and `subscribe`'s `pushManager.subscribe({applicationServerKey: key})`) and is not observed anywhere: `case_cross_machine` POSTs both subscriptions itself with `curl` (verify.sh:6275-6300), so a page that passed *this* machine's key to every row would pass every arm; `case_pwa`'s needles do not name `applicationServerKey`; `npm test` cannot see `main.ts`. This matters because the failure is silent in production too — a subscription minted for one key cannot be delivered by a sender signing with another, so the symptom is "peer notifications never arrive". The gate's own header is honest about what it measures (verify.sh:6087, 6097-6103): the *route pair*, the *payload*, the *refusal* — never the page. **Fix:** two needles in `case_pwa`'s bundle loop (`verify.sh:4764-4774`), which is this repo's established way to measure a `main.ts` rule as bytes: `applicationServerKey` present on both calls, plus `"push/subscribe"` routed through `apiPath`; or lift the key↔route pairing into a tested `push.ts` function.

4. **P2 — the away state's *trigger* is untested.** `web/src/main.ts:2718` decides bullet 4's session-page arm with a literal string comparison (`upstream_unreachable`/`upstream_timeout`) in the untested file, and `main.ts:2516` decides the settings row's `away` fact the same way. The gate measures the route's `502` (verify.sh:6361-6380) and `push.test.ts` measures `pushState({away})`'s sentence, so the sentence is tested and the condition is not. The gate discloses the analogous gap for the delete arm ("what a gate can measure is the route pair", verify.sh:6392) but says nothing for this one. **Fix:** `isAwayCode(code)` in `transcript.ts` with a test (this is finding Standards-2's fix too), and one sentence in the missing build.md paragraph naming the DOM as unmeasured.

5. **P3 — a `both` machine offers itself twice in the picker.** `createTargets` (`transcript.ts:1300-1307`) prepends `LOCAL_HOST` and then adds *every* reachable registry row, without the filter `settingsSection` applies two screens over (`main.ts:2383-2386`, `isLocalRow`): "the registry has a row for the local machine when the seed names it, and a second row for one machine would be a second subscription to the same origin". Same argument, same machine: two entries that name one computer. **Fix:** filter `(row) => !isLocalRow(row.url, location.origin)` before mapping to names — `createTargets` would need the rows' `url`, which `HostRow` already carries.

## The five questions

**1. Anything that claims a per-machine behaviour measured with one machine or not at all?** Yes, three, and one that is narrower than its sentence:
(a) the worker's `host` in the notification data — ADR D3 claims it, `sw.ts:103` does not write it (**P0**);
(b) "a page labels its own row with the name the phone will show" and "a hub reads a peer's claim through the hop" — the seventh key has no reader and the page's `Health` does not declare it (**P1**);
(c) "the app subscribes per machine with that machine's key" — unmeasured; the gate subscribes with `curl` (**P1**);
(d) `case_cross_machine`'s "two endpoints … each machine's pair mints its own" — one browser key in the fixture (P3, Standards-9).

**2. `case_cross_machine`.** Hard-coding `machine_name` back to `local` reddens **two** arms — `$name/peer-health/name` (verify.sh:6267) and `$name/payload` (6359) — so the payload's source is genuinely measured. A per-machine subscribe that ignored the peer's key reddens **nothing**: the case never observes which `applicationServerKey` the page passes, and no `case_pwa` needle or `npm test` covers it (Spec-3). There is **no** `SKIP` that masks the feature: all three fire on a missing `openssl`/`node`/`python3` (6119-6131), never on a deleted feature — so the P1 shape the brief warns about is not here. The missing `openssl` skip is worth noting only because it is the *only* in-gate measurement of the payload.

**3. The away arms.** The **settings row** is not a `false` claim *once read* — `pushState({away})` is a genuine third arm with its own sentence and label — but it **is** a false claim *before* the read ("not subscribed" at first draw, Standards-6), and its sentence arrives with the code in front although the story says it drops it (Standards-2). The **session page** invents nothing (Standard-4: back link, machine label, the machine's own message, one reload) but its trigger is untested (Spec-4), and its `.state` slot borrows the reach word (Standards-7). The **list's** half is HS-071's and was already right (`fillGroup`'s sentence alone, `COUNTS_UNKNOWN`'s `—`).

**4. The settings DOM.** Yes — the local row keeps all four ids and `case_pwa`'s needles still discriminate (see Observations). The `busy` rule keeps per-row controls unreusable-during-flight, deliberately: `act` early-returns and every action is `disabled`. The gap is truthfulness, not reuse: the row's word is drawn before its read (Standards-6). The rows' `row.key` is `undefined` until a read answers and `null` when the machine answered "no pair", so the two facts are not conflated — that part is right.

**5. Rules in `main.ts` that `push.ts`/`transcript.ts` should own.** Three: the `PushAction` → row-word cascade (`main.ts:2417-2429`) belongs beside `pushState`/`MachineSubscription`; the two-upstream-code test (`main.ts:2718`) belongs beside `hostFailure`, which is where the sibling rule already lives; and the only new user-visible prose outside a tested module — `` `the registry could not be read, so other machines are missing: …` `` (`main.ts:2741`) — should be a constant or a function in `transcript.ts`, as `NO_CREATE_TARGET`/`AWAY_DETAIL`/`STREAM_LOST`/`startLabel` correctly are. The first two are also the fix for the unmeasurable arm in Spec-4.
