## Standards

**Correct (with evidence).**

- One decision, two call sites, and the second hop really is gated: `http::app::edge` asks it (`src/http/app.rs:847-863`) and `preview::handle` asks it before `Route::strip` (`src/preview.rs:806-830`). There is no third door: `App::new` is still the one `Router::layer` and still the one production construction (`src/commands/serve.rs:537`), and the preview listener is the byte tunnel `preview::serve` owns.
- The address is not a header: `ConnectInfo<SocketAddr>` (`app.rs:855-859`) and `TcpStream::peer_addr` (`preview.rs:808`) are the only sources, and the absence of an address is a refusal, not a pass (`trust.rs:113-117`), matching `docs/notes.md:2520-2522`.
- The child is `hosts::probe`'s shape and has a deadline: `try_wait` against `WHOIS_TIMEOUT` with `kill`+`wait` on expiry (`trust.rs:285-302`), pipes read only after the child has exited (`trust.rs:307`). Nothing on the request path can hang indefinitely.
- Errors stay one envelope with codes from `src/http/error.rs` (`error.rs:62,72`), and the preview listener answers plain text with no envelope (`preview.rs:1062-1071`), per ADR-0051.
- No sentence names the configuration; the daemon's English rides in the log field only (`trust.rs:200-206`, asserted by `tests/trust.rs:180-190` and by the gate at `verify.sh:5828-5833`). This is measured, not claimed.
- The case owns its state: `stop_serve` first, own `$root` under `target/`, `rm -rf "$root"`, `PATH="$saved_path"`, `unset HS_TRUST_*`, `start_serve` last (`verify.sh:5703-5706, 5902-5906`) — the convention `case_forward`/`case_hosts` already follow, and the thing PER-101 finding 6 faulted.
- `case_verification_table`'s `continue` removal leaves no dead variable and no weakened rule (`verify.sh:544-589`), and the `python3` SKIP is honest here because `tests/trust.rs` is a genuine second witness (`verify.sh:5695-5702`), unlike PER-101 finding 2.

**Finding: minor — `trust::Refusal::code()` is a second spelling of codes that live in `http/error.rs`.**
`crates/holosmith/src/trust.rs:192-197` returns the literals `"peer_not_allowed"` / `"peer_unverifiable"`, while `crates/holosmith/src/http/error.rs:62,72` already defines `PEER_NOT_ALLOWED` / `PEER_UNVERIFIABLE`. The standard: `docs/notes.md:545` — "**Errors are one envelope**, `{"code","message"}` (ADR-0008); codes are constants in `http/error.rs`." Nothing but the gate's two literal greps (`verify.sh:5820-5821, 5837-5838`) ties the two spellings together. Smallest fix: have `code()` return `crate::http::error::PEER_NOT_ALLOWED` / `PEER_UNVERIFIABLE`, keeping the `preview_peer_*` spellings where they belong (`preview.rs:258-262`).

**Finding: minor — two documents say "four test literals"; the diff changed twelve sites.**
`docs/adr/0075-machine-trust-verifies-the-address-it-can-see.md:136` ("four test literals had to say so") and `docs/notes.md:2529-2531` ("four test literals that built the struct field by field"). The diff shows seven literals that name `tailscale:` (`tests/preflight.rs:80,215`, `tests/doctor.rs:110,126,341,1160`, `tests/deploy.rs:145`) and five more that gained `..Tools::default()` (`tests/disk.rs` ×5). The standard is "comments say *why* and cite the measurement". Smallest fix: say "seven literals name it; five more take `..Tools::default()`", or drop the count.

**Finding: minor — the spec still describes the gate rule this diff deleted.**
`HolosmithSpec.md:405`: "`case_verification_table` fails the gate when a row still says 'not yet run', … **or when V11 stops saying it is deferred**." That last clause is gone from the code (`verify.sh:547-554`), and ADR-0075 D9 says so. The spec is the top authority in this repo and now misdescribes its own gate. Smallest fix: delete the clause from `HolosmithSpec.md:405` in this same commit.

**Finding: nit — `Trust::with_program` has no caller.**
`crates/holosmith/src/trust.rs:93-97` ("the seam a test points at a shim") is used by nothing: the unit tests go through `Trust::of(&config, &tools)` and the integration tests through `Guards::from_config_with`. Speculative generality; delete it or use it.

**Finding: nit — a unit test whose name claims more than it does, and one assertion that restates its constant.**
`crates/holosmith/src/trust.rs:632-643` is `every_refusal_has_a_status_a_code_and_a_sentence`, but it constructs only `Refusal::NoPeer`; and `assert_eq!(refusal.status(), 403)` (line 636) compares `status()` to the value `status()` returns — a change-detector, not a measurement of the answer. Smallest fix: loop the three variants, and assert the *envelope's* `code` against `ApiError::from(&refusal)`.

**Finding: nit — `preview::Context::of` hard-codes the `Tools` the boot's comment says is one value.**
`src/commands/serve.rs:311-318` says "the guards resolve the trust check from the same `Tools` the state carries, so a boot with a shim … is one value rather than two spellings of one", but `preview::Context::of` builds its own `tools: crate::preflight::Tools::default()` and derives `trust` from that (`src/preview.rs:585-593`). No behaviour changes today because both are `Tools::default()`, so this is a comment that claims a property the code does not have for the second hop; either pass the run's `tools` into `Context::of` or narrow the sentence.

**Finding: nit — three matches on the same `trust::Refusal`.** `trust.rs:192-197`, `error.rs:950-958` and `preview.rs:258-262` each re-spell the same variant split. Optional: `ApiError::new(StatusCode::FORBIDDEN, refusal.code(), refusal.sentence())` collapses the middle one to a line.

## Spec

**Correct (with evidence).**

- Bullet 2's *implementation* is the story's letter: identity is the LocalAPI's answer about the socket address, folded to the node's short name (`trust.rs:343-352`), never `UserProfile.Login` — and that decision is pinned by a test that would go red if the login were compared (`trust.rs:520-529`). The child's argv is the proof the address (and nothing the caller wrote) was asked about (`trust.rs:452-458`, `verify.sh:5800-5804`).
- An unreadable identity is a refusal, never an admission (`trust.rs:123-128`), and the risk row records both "off when the list is empty" and "cannot verify where `tailscaled` does not answer" (`HolosmithSpec.md:444`) — the ADR-0054/ADR-0028 "say the unmeasurable thing out loud" rule.
- Bullet 5 is measured on both hops: the peer address and the reason in one `warn` (`trust.rs:236-248`), and the answer names no configured entry — with `workshop`/`attic` chosen precisely because the sentence's own "hub" is English (`tests/trust.rs:161-190`, `verify.sh:5831-5836`).
- The `GET`/`HEAD /api/health` exemption is safe and load-bearing: the payload is `name`, `version`, `role`, `uptime_s`, `preview_origin`, `application_server_key` (`src/http/health.rs:39-46`) — no config, no secret — and a hub's registry is filled by exactly that call (`ADR-0075` D1).

**Finding: blocker — every forwarded call arrives as the front door, so `allowed_hubs` cannot refuse one.**
`crates/holosmith/src/trust.rs:119-121` admits `127.0.0.1`/`::1` unconditionally, and that is the address a deployed hub's call comes from: deploy step 6 publishes the control origin by proxying **to loopback** — `crates/holosmith/src/deploy.rs:1731-1733` (`control_target` → `format!("http://127.0.0.1:{}", config.control_listen.port())`) and `HolosmithSpec.md:373` ("Configure `tailscale serve` for the control origin (443)"). A peer whose registry row is its own `control_origin` — which ADR-0074 D4 requires be "the exact `control_origin` the machine reports", and a loopback one could only ever name the hub itself — dials `https://<peer>.tail.ts.net`, `tailscaled` accepts and reconnects from `127.0.0.1`, and the new check answers `Admitted::FrontDoor` with no whois at all. The repo's own two-machine model shows the same arrival address: `verify.sh:5228-5229` seeds the hub's row as `url = "http://127.0.0.1:$peer_control"`. So the sentence this rests on — `HolosmithSpec.md:102`, "a machine accepts forwarded calls only from peers listed in `allowed_hubs`", and bullet 4's "the whois check accepts the hub and rejects another tailnet node" — holds only for a caller that dials the listener's loopback socket directly, which no deployment accepts a remote node on. ADR-0075 D3 makes the omission visible rather than covering it: it enumerates "*every browser call, every `holosmith` CLI call, `doctor`, a host probe and the gate*" as what arrives from `127.0.0.1` (`docs/adr/0075-machine-trust-verifies-the-address-it-can-see.md:67`) — the one arrival it leaves out is the forwarded call the story exists to govern. Neither the V11 cell (`HolosmithSpec.md:421`), the new risk row (`HolosmithSpec.md:444`) nor D8's cost list mentions it, so the record claims a check that the shipped topology does not exercise.
Smallest fix (the code fix is a design decision, not a one-liner): record it now — a risk row plus a sentence in V11's cell and in D8 — that `allowed_hubs` is enforced for a direct dial only, and that a peer reaching the machine through `tailscale serve` is a front-door caller; the alternative (a registry row naming a `100.64/10` address with the listener bound beyond loopback) is a follow-up story, not this one.

**Finding: major — the forged-header arm cannot fail, so bullet 2's "not by a header the caller supplies" is asserted, not measured.**
`scripts/verify.sh:5845` sends `Tailscale-User-Login: me@example.com` while the shim answers `stranger`, and `crates/holosmith/tests/trust.rs:208` does the same; both expect `403 peer_not_allowed`. A header-honouring implementation would also answer `403`, because `me@example.com` is not a listed name — and a hypothetical `admit` that *also* honoured a header naming a listed hub would pass **every** arm in the suite: the listed-node arm (200) still passes, the stranger arm (403) still passes, and this arm still passes. ADR-0075:120 claims of this arm, "unchanged: still `403`, because a claim is not a verification"; that is not what the arm measures. Smallest fix: forge the **listed** name — `Tailscale-User-Login: workshop` (and, in the test, a config whose list holds the forged value) — so a header-trusting implementation is served and this one still refuses.

**Finding: minor — "one logged line" is claimed but never counted.**
`verify.sh:5818` ("refused, in the envelope, **once** in the log"), `HolosmithSpec.md:421` ("one logged line naming the peer"), ADR-0075 D4 ("One `warn` per refusal") — the checks are `grep -q` (`verify.sh:5834-5839`), which pass on any number of lines, including the two the same refusal already writes if the `spawn_blocking` arm were ever hit. Smallest fix: `[ "$(grep -c 'a call from a peer this machine does not trust was refused' "$WORK/serve-peer.err")" = 1 ]`.

**Finding: nit — bullet 3's "forwarded calls carry the verified identity" is deliberately not implemented, and it is recorded rather than discovered.**
`docs/adr/0075-machine-trust-verifies-the-address-it-can-see.md:99-107` (D5) decides that no identity header travels and that the peer verifies the address it can see; `forward::request_head` is untouched (`src/forward.rs:198`). That is a defensible reading of item 4's own sentence, and it is written down, so I record it as a known deviation rather than a defect — but the acceptance checkbox as written is not literally satisfied, and V11's cell would be more honest saying "the peer re-verifies the address instead of carrying an identity".

---

**Merge verdict: BLOCK** — Standards has no blocker (four minors/nits, all small and local); Spec has one: the front-door arm swallows exactly the call the story exists to refuse on a deployed machine (`trust.rs:119` + `deploy.rs:1731-1733`), and the V11 cell, the risk row and ADR D8 do not say so.

Worst issue per axis: Spec — S1 (blocker). Standards — the code-constant duplication (`trust.rs:192` vs `error.rs:62,72`), which the repo's notes make a rule.

Test commands a supervisor should run (I cannot): `cargo test -p holosmith --test trust --test preview --test forward --test guards --test preflight --test doctor --test disk`; `cargo clippy --all-targets -- -D warnings`; `scripts/verify.sh` (at minimum `case_machine_trust` and `case_verification_table`, the latter to confirm V11's cell still passes the four rules after the deferral rule's removal).
