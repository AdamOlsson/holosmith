### 1. **blocker** — the percent-decoded path lets a caller author the peer's request head

**Where:** `crates/holosmith/src/forward.rs:188` (`head.push_str(request.rest)`), fed by `crates/holosmith/src/http/forward.rs:97` (`rest: &rest`, the axum `Path<(String, String)>` capture).

**What is wrong:** axum 0.8.9 percent-decodes every `Path` parameter before it reaches the handler — `axum-0.8.9/src/util.rs:13-24` (`percent_decode(...)` in `PercentDecodedStr::new`) and `src/extract/path/de.rs:46` (params are `PercentDecodedStr`). So `GET /api/hosts/workshop/sessions%0d%0atailscale-user-login:%20owner@example HTTP/1.1` gives `rest = "sessions\r\ntailscale-user-login: owner@example"`, and `request_head` writes those bytes into the request line it sends the peer. `http/forward.rs:72`'s `rest.split('/').next() == Some("hosts")` refuses only the literal `hosts` segment; nothing else inspects `rest`.

**Why it matters:** ADR-0074 D4's whole claim is "the hub **authors** the call" and names exactly the headers that "do not travel": "the caller's `Host`/`Origin`, `Expect` and `tailscale-user-login`" (`docs/adr/0074-…md`, D4). With one percent-escaped CRLF they all travel again — and `tailscale-user-login` is the peer's owner check (`src/http/guard.rs:20`, `95-110`), which D4 itself records as "vacuous for a forwarded call" and hands to HS-070. A `GET` needs no `Origin` or client header (`guard.rs:82-84`), so any tailnet client that can reach the hub can inject. This is the one seam HS-070 is about to start trusting.

**Smallest fix:** refuse in `respond`, not in `request_head` (`None` there already means "not an origin"): after the `local`/`hosts` checks, `if rest.bytes().any(|b| b < 0x21 || b == 0x7f) { return ApiError::not_found().into_response() }`. The faithful alternative is to take `rest` from `parts.uri().path()` and strip the `/api/hosts/<name>/` prefix raw, so the peer sees the client's own encoding. **What turns red:** a `tests/forward.rs` arm that sends `GET /api/hosts/{PEER}/sessions%0d%0aX-Injected:%201` and asserts `!peer.asked().contains("X-Injected")` — it is red today.

### 2. **major** — the gate returns before every arm on a machine with no `python3`, and §7 is acceptance bullet 6's only witness

**Where:** `scripts/verify.sh:5166-5177`. Line 5166 says "The API half below needs nothing, so only the preview arms are conditional", and line 5174-5176 then returns before any arm unless `python3` exists.

**What is wrong:** `python3` is needed by three arms only — `hosts_field` (§1), the silent peer (§4's `504`) and `stream.py` (§3). §2 (the create, the `Idempotency-Key` replay, the byte-for-byte `cmp`), §4's other four refusals and the whole of §7 (the `kill -9` mid-stream arm, lines 5633-5654: `exec {fd}<>`, `timeout`, `kill -9`, `read -t`) need none of it.

**Why it matters:** `phase_serve` withholds a case's `ok` line whenever the case prints `^SKIP` (`verify.sh:10846-10859`), so one missing tool removes the case entirely — and `tests/forward.rs` explicitly does not cover the death arm ("What is **not** here … a peer killed mid-stream", module doc). Bullet 6 ("a clear client-visible error, not a hang") therefore has **no** measurement at all on a python3-less machine. `docs/build.md:510-514` claims the opposite in as many words: the API half "needs no daemon … which is what makes this case run everywhere".

**Smallest fix:** split the guard the way `case_server_service`/`case_deploy` do (`build.md:553`, "two halves that skip independently and print one `SKIP` line each"): keep `python3` for §1/§3/§4's silent arm with their own `SKIP case_forward/python3…`, and let §2, §4's other refusals and §7 run.

### 3. **major** — the byte-for-byte row comparison races the stub's provisioning

**Where:** `scripts/verify.sh:5345-5350`; `forward_wait_idle` is defined at 5291 and first **called** at 5356.

**What is wrong:** the create at 5324 returns `202` with a `starting` row and "provisions in the background" (the case says so at 5354). §2 then reads `GET /api/sessions/$id` from the peer and the same row through the hub and `cmp`s them. A `status` flip (`starting → idle`) or an `updated_at`/`usage_*` change between the two reads makes the two documents legitimately different and the case red on a correct build.

**Why it matters:** a gate arm that can fail for a reason that is not the code is the shape this project rejects (`docs/build.md:616`, "a case that must assert one code keeps every higher guard check correct, or it asserts another guard's code under its own name" — the same rule about attribution). It is also a flake that will be re-run and hand-waved.

**Smallest fix:** move `forward_wait_idle` (one line, already defined) to just before 5345, which is also the assertion the arm wants — "the same row, both ways, once it has settled".

### 4. **minor** — the event-stream test's second assertion cannot fail

**Where:** `crates/holosmith/tests/forward.rs:380-383`.

**What is wrong:** `assert!(answer.header("transfer-encoding").is_none() || answer.body.contains(EVENTS))` — the right-hand side is already asserted at 376, so the whole line is a no-op. It cannot be tightened to `is_none()` either, because hyper re-frames a length-less body as chunked, and `tests/support/mod.rs:318-342`'s `parse` does **not** de-chunk. So nothing here distinguishes "the hub decoded the peer's chunks and framed the answer itself" from "the hub copied the peer's chunked bytes verbatim": `EVENTS` appears in both.

**Why it matters:** the assertion's own message ("the answer is framed by this machine, not by the peer") is the claim of ADR-0074 D8/D1, and it is unfalsifiable. The behaviour *is* measured — by the gate's `stream.py` decode + `cmp` — but this test is presented as the unit-level proof.

**Smallest fix:** de-chunk `answer.body` in the test (ten lines, or lift the decode into `tests/support`) and `assert_eq!` against `EVENTS`. **What turns red:** change `Framing::Chunked` handling in `BodyStream` to pass bytes through (`Decode::UntilClose`) — that mutation leaves today's test green and would turn the honest one red.

### 5. **minor** — `stop_peer`'s exit-code check can never run in the only case that calls it

**Where:** `scripts/verify.sh:10797-10802` (`stop_peer` ends with `check "peer/exit" 0 "$status"`), versus `5647-5648`, where §7 does `kill -9 "$peer_pid"; wait; peer_pid=""` before the case's closing `stop_peer` (5662).

**What is wrong:** `stop_peer` opens with `[ -n "${peer_pid:-}" ] || return 0`, and `peer_pid` is already empty by then — so the `peer/exit` assertion the function exists for (its doc: "so a hub's peer is as well-behaved as a hub") never executes. Deleting the whole `check` line leaves the gate green.

**Smallest fix:** either re-boot the peer after §7 and then `stop_peer`, or move §7 to a peer of its own (`start_peer` a second one) — or, if the exit code is deliberately not this case's business, drop the dead `check` and say so.

### 6. **minor** — `case_forward` never removes its scratch tree

**Where:** `scripts/verify.sh:5656-5666`. Every other boot-owning case ends with `rm -rf "$root"` (`case_hosts` 5107, `case_push` 4579, `case_schema_newer` 3239, `case_uninstall` 10695 …).

**What is wrong:** a passing run leaves `target/verify-forward-<pid>/` — two data roots (a hub database with four rows, a peer database with a session and its event log), two configs, the seed, `silent.py`/`stream.py` and the event dumps. The stand-in is also `kill`ed without the `wait` that the same idiom uses in `case_push` (4576-4578).

**Smallest fix:** `rm -rf "$root"` immediately before the closing `start_serve`, and `wait "$standin_pid"` beside the `kill`.

### 7. **minor** — the HS-021 case's comment is orphaned 537 lines above its function, and one of its sentences is now false

**Where:** `scripts/verify.sh:5112-5130` (the `case_idle_stop` block ending "slot they assume.") immediately followed by `5131`'s HS-069 comment and `case_forward`, with `case_idle_stop` itself at `5668`.

**What is wrong:** after the insertion a reader meets `case_idle_stop`'s doc block as the *prelude to `case_forward`*, and its claim "It runs right after `case_delete_session`" is no longer true.

**Smallest fix:** move the HS-069 comment block plus `case_forward` above line 5112 so the HS-021 block sits on its own function.

### 8. **minor** — a body over the forwarding limit answers the create's sentence

**Where:** `crates/holosmith/src/http/forward.rs:88` (`ApiError::bad_body()`), `crates/holosmith/src/http/error.rs:381-388`.

**What is wrong:** a forwarded body over `BODY_LIMIT` (2 MiB) gets `422 bad_body` with "the body must be a JSON object with `project`, `model`, `thinking` and optionally `network`" — a create's sentence about a request that is not a create.

**Why it matters:** ADR-0008's own rule, applied three times already in this file: "the code is the API and the sentence is prose … a client that told the operator the create's fields would be describing the wrong request" (`error.rs:391-397`, `bad_prompt`/`bad_steer`).

**Smallest fix:** a `bad_forward_body()` in that family (`422`, `BAD_BODY`, a sentence naming the 2 MiB bound and this route).

### 9. **minor** — a chunked reply's stale `Content-Length` is copied onto this machine's answer

**Where:** `crates/holosmith/src/forward.rs` — `keep_header` keeps `content-length` unconditionally, while `framing_of` gives chunked precedence over a length; the unit test at `the_answer_is_its_head_and_whatever_arrived_behind_it` constructs exactly such a head.

**What is wrong:** for a peer that sends both headers, the hub decodes the chunks (so the body is the de-chunked length) and then relays the peer's `Content-Length: 3` onto that body. hyper honours a caller-set length on a streaming body, so the answer is truncated or the connection is mangled — the "silently wrong" reply the story is supposed to make impossible. Unreachable against this build's own hyper (which never emits both), which is why it is minor.

**Smallest fix:** in `http/forward.rs:139-152`, skip `content-length` unless `reply.framing == Framing::Length(n)` and the header parses to `n`.

### 10. **minor** — two test/gate call sites do not report their own failure

**Where:** `scripts/verify.sh:5345` (`forward_fetch` with no `|| fail`), and `crates/holosmith/tests/forward.rs:647` (the comment "and no `Origin` on a plain GET").

**What is wrong:** `forward_fetch` returns `1` on a dial failure and nothing reads it; the run then dies at the `cmp` with `FAIL case_forward/row/bytes`, blaming the hub's row for a connection that never opened. And the peer arm always sets `Target::origin = Some(...)` (`preview.rs:960-969`), so `rewrite` writes `Origin: <peer preview origin>` on a plain GET too — the comment asserts the opposite of what the code does, and no assertion covers it either way.

**Smallest fix:** `|| fail "$name/direct" …` on 5345; and either drop the comment clause or make it an assertion.

### 11. **nit** — a stale doc comment left by the change

**Where:** `crates/holosmith/src/preview.rs:184-186`, on `Refusal::UnknownHost`: "`/<host>/…` names another machine; this one serves only its own sessions (HS-069 forwards the rest)".

**What is wrong:** `Route::strip` no longer refuses on the host and `plan` now returns this only for a name the registry does not hold; the variant's own sentence (`preview.rs:213-218`) already says the new thing. Also unmeasured: on a machine whose config says `role = "server"` (the role `case_uninstall:10543` and this case's peer write), `plan`'s rule 2 answers before the row lookup, so `/api/health` on the preview listener is `403 preview_not_forwarded` — "so `api` is another machine's name and only a hub reaches it" — which is precisely the sentence the comment above `UnknownHost` says must not be written ("claiming `api` is a machine would be a sentence that is wrong about the thing it names"). `tests/preview.rs` and `case_preview` pin the `404` for `Role::Both` only.

**Smallest fix:** reword the variant comment; and either check the row before the role in `plan` (unknown name stays `UnknownHost` on every role) or add a `Role::Server` assertion to `a_previews_four_refusals_…` so the answer is a decision rather than an accident.

### S1. **minor** — bullet 4 gains a third slow arm the spec does not name
`forward.rs:104-118` gives `DELETE sessions/<id>` the 60 s bound; item 3's sentence is "merge and publish use 60 s". ADR-0074 D6 argues it from the peer's `abort_grace` and `the_two_slow_arms_are_the_specs_and_the_deletes` pins it, so this is a recorded deviation, not a defect — flagged so the verdict in the verification table names it. No fix.

### S2. **major** — bullet 6 can be unmeasured (cross-ref Standards 2)
The only witness is `case_forward` §7, and the case's first guard returns before it. `tests/forward.rs` is explicit that the death arm is the gate's. Nothing else in the suite would notice if a forwarded stream parked forever. Fix as in Standards 2.

### S3. **minor** — ADR-0074 D9's refusal order is not the code's
D9 says the hub's create is answered "**before** the idempotency lookup and before the disk floor", and the case comment (`verify.sh` §5) and `tests/forward.rs::a_hub_creates_no_sessions_of_its_own` say it is answered "before the body is even looked at". `sessions.rs:262` parses the body first, and `create_locked` (`sessions.rs:554-565`) runs `by_client_key` *before* raising the refusal — the comment on the function says so ("`create_locked` raises it after the key's lookup"). Unobservable on a hub that never held rows, but observable if a machine's role was changed from `both` to `hub` with rows behind it: a retry then answers `202` with the old row rather than `403 sessions_disabled`. Smallest fix: correct D9's sentence (the place is "first of the machine's refusals"), or hoist the role check above `slot_for` if the stricter reading is wanted.

### S4. **nit** — a document claim the tests do not keep
ADR-0074 D4 says the exact-`control_origin` prerequisite is measured by "`tests/forward.rs` and the gate's `case_forward`". Only the gate's `wrongspelling` arm measures it; `tests/forward.rs` has no `bad_origin` arm at all (grepped). Also `docs/build.md:520` and `scripts/verify.sh:5152-5156` both say "the five refusals with five codes" and then list six arms. Smallest fix: drop `tests/forward.rs` from D4's sentence, and say "six arms, five codes" (or stop counting the `308` as a refusal, which D3 itself says it is not).
