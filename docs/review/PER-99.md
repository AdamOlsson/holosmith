### Findings

`Spec · minor · docs/adr/0072-…md:63-79 (D9) vs docs/build.md:482` · The two documents disagree about who measures the install. `build.md:481-482` says "What it cannot see is the tap, the notification **and the install itself**: those are `web/test/push.test.ts`'s 25 rules and the demo's (ADR-0072)", but D9's demo sentence names only "a real `push` event delivered to the registered worker, the notification appearing, and the click opening `/sessions/<id>`" — never the install prompt. This matters because D4 deliberately ships **no `fetch` handler**, and Chrome's documented install criteria have historically required the registered worker to *have* one; if the operator's Chrome still applies that check, `beforeinstallprompt` never fires and acceptance bullet 1 ("valid installable PWA") is true only as bytes — which is exactly what `case_pwa` can see. Nothing in this repo can settle it, and `/tmp/holosmith/demo` is empty here, so no demo evidence is in this checkout. **Fix:** run the install once in Chromium as part of the demo, record the answer with the Chrome version in `docs/notes.md`, and make `build.md:482` and D9 name the same three-or-four things.

`Spec · minor · web/src/push.ts:150-161` · `pushState` tests `permission === "denied"` **before** `facts.subscribed`, so a browser that still holds a `PushSubscription` after the operator blocked notifications for the site lands in the `blocked` arm, whose `pushActionable` is `false` — the Unsubscribe button is never offered. That contradicts the function's own rationale at `push.ts:139` ("an existing subscription can always be undone, even on a machine whose pair has gone") and leaves a `push_subscriptions` row this machine keeps delivering to, which is the same stale-row state `main.ts:1999-2002` goes out of its way to avoid on the subscribe path. No arm covers it (the order test at `web/test/push.test.ts` covers `subscribed:true, hasKey:false` but not `denied + subscribed`). **Fix:** move the `subscribed` arm ahead of `denied` (or let `pushActionable` be true while subscribed), and add the missing arm to "the arms' order is what makes the sentences true".

`Standards · minor · scripts/verify.sh:1421, crates/holosmith/src/doctor.rs:1158, crates/holosmith/tests/deploy.rs:245, docs/notes.md:1701` · Four comments still describe the health payload as five keys after it became six (`verify.sh:1421` "The health payload: exactly five keys"; `doctor.rs:1158` "`Health`'s five keys"; `deploy.rs:245` "`Health`'s five keys, because the reader parses them"; `notes.md:1701` "The health payload is `Health`'s five keys"). ADR-0072 D1 priced exactly this: "the payload's test and 'the machine's five keys' prose move with it". `case_health`'s assertion is a prefix-plus-`}` match so the gate still passes — the prose is simply now false. **Fix:** say six (or "the first five, unchanged") in all four; `tests/http_contract.rs:38`'s "the five keys before it keep their order" is already correct.

`Standards · minor · crates/holosmith/src/web.rs:100-103` · The new embed test returns silently unless `HOLOSMITH_REQUIRE_WEB=1`, and nothing in the documented gate sets it for `cargo test`: `scripts/build.sh:60` exports it only around `cargo build --release`, and `scripts/verify.sh`'s `run_phase test cargo test` runs before that with the variable unset. So under `scripts/verify.sh` this test's body never executes and a regression in the embedded manifest/worker/icons is invisible to it — which is the shape `RESUME.md:1221` warns about ("a test that cannot fail is worse than no test"). `case_pwa` is the real coverage, so nothing is uncovered; the test is just inert where it looks load-bearing ("in a real build"). **Fix:** export `HOLOSMITH_REQUIRE_WEB=1` for `cargo test` in `verify.sh` (or give the early return a visible trace so a reader knows it did not run).

`Standards · minor · scripts/verify.sh:4702-4720` · The ten id needles are written `'id="settings"'`, `'id="settings-machine"'`, …, but the source spells them `machine.id = "settings-machine"` (`web/src/main.ts:1858` etc.) with spaces. They match only because the app bundle is minified (`web/vite.config.ts` has no `minify` key, so Vite's default `esbuild` is on) — and the *worker* config deliberately turns minification off and says why (`vite.sw.config.ts:17-18`). Anyone flipping `minify: false` on the app build reds `case_pwa_asset/settings` with a message ("the served bundle does not carry id=\"settings\"") that points at the wrong thing. **Fix:** state the dependency in the comment beside the loop (as the worker config does), or use a needle shape that survives both (`\"settings-machine\"` plus the assignment, or grep for the id alone).

`Standards · minor · web/tsconfig.json:19` · `"include": ["src", "vite.config.ts"]` lists the app's Vite config explicitly but not the new `web/vite.sw.config.ts`, so the one new file in `web/` is the only one `tsc --noEmit` never checks. **Fix:** add `"vite.sw.config.ts"` to `include`.

`Standards · minor · web/src/main.ts:1996, 2022` · Both new mutating requests re-spell `{ "content-type": "application/json", "x-holosmith-client": "1" }` although `main.ts:1149` declares `const JSON_HEADERS` documented as "The headers every mutating request carries (the guards read the content type as well)", and the Changes sheet's four fetches use it (`:1463`, `:1510`, `:1539`). **Fix:** use `JSON_HEADERS` in both.

`Standards · minor · GLOSSARY.md:948` · "Its every word is a `web/src/push.ts` function with a node test" is false for four strings on the screen that this change set adds to `main.ts`: the heading `make("h2", "", "Notifications")` (`:2062`), the busy label `"Working…"` (`:1901`), the notice shape `` `${code}: ${message}` `` (`:1963`), and the two refusal sentences (`:1979` "this app's service worker is not running, so nothing could be subscribed", `:1991` "…carried no p256dh/auth pair"). None of the five has a node test. **Fix:** narrow the sentence to what `push.ts` actually owns (the state sentence, the detail, the action label, the row, the iOS sentence) and say the heading and the two refusals are the page's.

`Standards · nit · crates/holosmith/tests/http_contract.rs:47-50` · `tail.contains("\"B")` accepts any string that begins with `B` (`"Bogus"` passes), so the assertion cannot catch a truncated or wrong key — it only distinguishes key-from-null. It is loose because `support::state()` (`tests/support/mod.rs:96-97`) sets `config: Config::default()`, so `application_server_key` is a fact about the developer's machine — precisely the hazard `health.rs:157-159`'s own comment calls out and works around with a `TempDir`. **Fix:** give this test its own state on a `TempDir` data root (as the unit test does) and assert `null` and then the written pair exactly.

### Verdict

**OK with notes.** No blocker and no major: I could not find a defect that breaks an acceptance bullet, a route contract, or the gate. Every finding is prose-or-consistency or an untested edge; the two I would actually fix before closing are the `denied + subscribed` arm (`push.ts:150`, a real dead end for an operator) and the four stale "five keys" comments, because ADR-0072 promised that prose would move.

### Verified as correct (so you can see what I read)

- **The new reader and the case's hand-written pair are safe together.** `vapid::public_key` (`vapid.rs:141-144`) is exactly "one answer for two states", and `parse` (`:58-82`) validates only through `is_well_formed` (`:173-176`) — 65 bytes starting `0x04`, 32-byte scalar. So `case_pwa`'s literal (`verify.sh:4560-4561`, 87 chars, decoding to `0x04‖0x01..0x40`) is accepted even though it is **not** a point on P-256; that case sends no push, so the DER walk is never exercised. The 87-character claim is independently pinned at `vapid.rs:330`.
- **The wire contract the screen calls is the server's own.** `POST /api/push/subscribe` takes exactly `{endpoint, p256dh, auth}` and answers `204`; `DELETE …?endpoint=` percent-decodes and answers `204`/`404` (`http/push.rs:54-111`), matching `subscriptionBody`'s flattening and the `?endpoint=` `URLSearchParams` call; both fetches carry the two headers `guard.rs:79-94` demands of a non-GET. And the id rule agrees with the server: `push.ts`'s `/^[0-9a-f]{16}$/` is the same predicate as `sessions::is_id` (`sessions/mod.rs:85-90`, `len == 16 && is_ascii_hexdigit() && !is_ascii_uppercase()`).
- **Every path the case fetches is reachable and distinct.** `app.rs:817-833` tries `web::asset` before the shell, so `/manifest.webmanifest`, `/sw.js` and `/icons/*.png` are the embedded files (not the fallback) and `/settings` is the shell; `web::content_type` (`web.rs:53-66`) now maps `webmanifest`; and `sessionIdFromPath` (`transcript.ts:783-791`) demands exactly three segments, so `/settings` reaches the new branch rather than the session one. `case_push` ends with `stop_serve; start_serve` (`verify.sh:4545-4546`) and its three SKIP paths return before its own `stop_serve` (`:4039-4050`), so `case_pwa`'s opening `stop_serve` always finds a pid.

**Commands the supervisor must run** (I have no shell): `cd web && npm test && npm run build` (25 new tests + the second Vite config), `cargo test`, `HOLOSMITH_REQUIRE_WEB=1 cargo test --lib web` (the only way `web.rs:100`'s body executes), and `scripts/verify.sh` (for `case_pwa`, `case_health`, `case_push`, `case_app_shell`, `case_changes_screen`).
