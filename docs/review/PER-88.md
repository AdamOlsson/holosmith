*Smallest fix:* assert a needle only the next-step half carries — `message.contains("ask the agent to commit")` in the test, `grep -qF 'ask the agent to commit'` in the gate (or pin the whole sentence in `http/merge.rs`'s unit tests, where a sentence is cheap to pin).

## Spec axis (PER-88 / HS-056 acceptance, `HolosmithSpec.md` item 12 rules 1, 5, 6, ADR-0065 D1–D10)

### Findings

**P1 — `delete_session: true` can permanently delete a branch whose commits are *not* in the target.**
`crates/holosmith/src/http/sessions.rs:1077-1086`: the override is strategy-blind — `(Retained::Known { wip, .. }, Some(_)) => Known { branch: None, wip }` — and `Retained::keeps_branch()` then makes `Worktree::remove` run `git branch -D agent/<id>` (`worktree.rs:233-235`). Reaching it only needs the branch to have moved *past what the merge landed*, and the merge itself is explicit that the target moves to `head` read at `basis`, not to the branch's ref: `holosmith/src/merge.rs:468` (`let head = basis(worktree)?`) → `:480` (`is_ancestor(reference, &head)`) → `:505`/`:510` (write `head`). Both the module and `docs/notes.md:1948-1952` record this window as known and survivable **because HS-043's keep-rule then answers `Merged::No` and keeps the branch** (`worktree.rs:200-203`). The override throws that answer away: the branch — commits, not files, so no wip ref helps — is force-deleted, and only the reflog remembers. The rule-1 guard does not close the window: it is a one-shot read of `session.status` (`http/merge.rs:165`), so a prompt that arrives after it moves the row to `running` and an agent commit then lands mid-merge (for `merge`/`squash` the window spans `land`'s `worktree add` + merge + commit + `worktree remove`, i.e. hundreds of ms).
*Smallest fix:* carry the commit the landing used (`Merged`→`deletion`), and in `retained_for` drop the branch only when `Worktree::branch_head()` still equals it; otherwise leave `branch: Some(agent/<id>)` and log it. (Scoping the override to `squash` — the only strategy where the keep-rule is *wrong* by construction — also closes most of it and is a one-line change, but the tip comparison is the honest one.)

**P2 — D6's squash warrant is asserted, not measured: "the target's tree **is** the branch's tree" is not a git guarantee.**
`docs/adr/0065-…md:149` (the `squash` row of D6's table), repeated in `crates/holosmith/src/http/sessions.rs:1052-1055` ("its commit's tree is the branch's") and encoded as an assertion at `scripts/verify.sh:6060-6061`. A squash is a three-way merge of the branch into the target from their merge base: if the target has advanced on any path, the result keeps the target's content on that path and the trees differ while the branch's work is still contained. The gate's fixture cannot tell: by arm 5 `main` is the branch's parent (arm 4 fast-forwarded it), so tree equality is true for a reason that is not the invariant claimed, and extending the case to a target that had moved on would fail this check on a *correct* merge. The behaviour is defensible; the stated warrant is not.
*Fix:* restate the row as "the branch's changes are in the target" and measure containment (`git diff --quiet agent/<id> refs/heads/main -- $(git diff --name-only <base>..agent/<id>)`) instead of tree equality.

**P2 — D2's `deleting` row is not safe when the merge carries `delete_session`.**
`docs/adr/0065-…md:47` promises "its `Retained` was decided before the removal was spawned, so a merge here can neither lose the branch nor gain one". But the merge accepts a `deleting` row, and `sessions::deletion`'s already-`deleting` early return (`http/sessions.rs:988-996`) recomputes `retained_for(…, landed)` — branch forced to `None` — and spawns a **second** teardown, while the first teardown (holding the operator's `Retained`, which may keep the branch) is still in flight. The branch *can* be lost, and two teardowns race over the same worktree. Fix: either refuse `delete_session` on a `deleting` row, or pass `landed` only on the path this request transitioned, and say so in D2.

**P2 — the landmine this change depends on is now stale.** `docs/notes.md:1948-1952` still says the ancestry window is "reachable here because rule 1's `session_running` guard is HS-056's and deliberately **absent**". It is present now, and it does not close the window (one-shot check, above). Since that note is the only place the hazard's mitigation is written down, and this story removes that mitigation for `delete_session`, the note should say what remains: fixed by comparing the branch tip, not by the guard.

**P2 — the gate's squash tree check reads the worktree and branch *after* the delete has been spawned.** `scripts/verify.sh:6060-6061` runs `git -C "$wt" rev-parse "agent/$id^{tree}"` between the 200 and `wait_for_gone` (`:6062`), while `deleter().spawn` (`http/sessions.rs:1042`) is already removing exactly `$wt` and `agent/$id`. Losing that race makes `check` compare `""` against the target's tree and fail a green build. Fix: compare against the `$tip` captured before the request (the object survives the branch's deletion): `check … "$(git -C "$repo" rev-parse "$tip^{tree}")" "$(git -C "$repo" rev-parse "refs/heads/main^{tree}")"`.

**P2 — the two acceptance bullets the ADR declines are declined honestly, and one of them is verified.** Rule 6's 60 s: D8's claim "has no client in this build" is true — there is no `merge`/`publish` call anywhere in `web/src` (`web/src/main.ts` has no timeout at all, and no merge), no hub module in `crates/holosmith/src`, and `docs/stories/phase-3-multiple-machines.md:36` does carry "Default forwarding timeout is 5 s; merge and publish use 60 s". The claimed alternative is also right: a blanket 5 s on the shared client would cut the delete's own wait, because `abort_grace` defaults to 10 s (`config/mod.rs:272`) and `deletion` awaits `end_turn` before the snapshot. The commit-offer UI: correctly deferred to HS-058 with the prompt text named in D3. Both are recorded, not silently skipped — but see **S1**: the half of bullet 2 this story *does* claim (the sentence names a commit) is the half whose test cannot fail.

**P2 (note, not a defect) — arm 6a's mechanism is indirect.** `scripts/verify.sh:6121-6123` makes `snapshot::take` fail via `chmod 0555 $data/sessions`, which only works because `create_dir_all("<data>/sessions/<id2>")` (`snapshot.rs:108-113`) is the first write and `<data>/sessions/<id2>` happens not to exist (no container ever starts over the `_ping` shim, so `Exits::record` never writes `session.log`). It fails loudly if that changes, but asserting the directory is absent before the chmod would say which way it broke.

### What is good (Spec)

Every measurable bullet is actually measured, and measured on the artifact rather than on the code's own claim: `session_running` is produced through the table's own `Transitioner` (`tests/merge.rs:1671-1696`) and by writing one column in the gate, and the refused merge is proven to have moved *nothing* — target ref, branch ref, the agent's file, and `<data>/merge` **absent**, not merely empty, which is true by construction because both guards sit before the `spawn_blocking` task that reaches `land` (`http/merge.rs:186-200`); the negative half is a real measurement (`every_status_but_running_still_merges` drives five rows and would go red on `!= Idle` for four of them); the dirty guard is a *pre*-check for a reason ADR-0065 D3 argues rather than asserts, it uses the one definition of work the changes view uses, and the ignored-file arm is the test that keeps it from drifting to `--ignored`; the `basis`-before-`dirty` order exists so an `rm -rf`'d worktree answers `409 no_worktree` instead of a `500`, and it has its own test; `delete_session` runs the delete flow's request half (not a copy), moves the row to `deleting` before the 200 (`http/sessions.rs:1031`), hands the removal to a task, keeps the answer at exactly three keys, and a failed delete is logged rather than retracted — 200 standing, which the gate measures with an unwritable snapshot directory; the `deleting`/`running`/`error` decisions in D2 are argued against the spec's words ("while a turn runs") and against `not_in_state`'s one-code-per-state family; and the branch-deletion contrast (squash **with** the flag deletes, squash **without** it keeps and the ordinary `DELETE` says `kept.branch`) is measured twice in one case and honestly placed in the gate because the crate fixture's stub backend answers `Retained::nothing()` (`backend/stub.rs:460-466`, exactly as the new notes bullet says). The `wip` half of HS-043's `Retained` is still asked after the snapshot, and `Retained::Unknown` is untouched by the override — "cannot tell" still never means "delete".
