## Finding

**1. P1/major — `--config` and `--root` are handed to the target's login shell unquoted, so they do not in fact "travel verbatim".**
`crates/holosmith/src/remote.rs:469-475` pushes `config.display()` and `root.display()` as bare argv elements, and `remote.rs:250-254` extends the run child's argv with them; ssh joins everything after the host with spaces and hands the result to the remote login shell, so the target re-parses those two paths. Consequences, in order of severity: (a) any glob/match turns into a *different* path silently — `--root '/srv/holo*'` deploys into whichever tree matches; (b) shell metacharacters are executed on the target (`--root '/tmp/x; …'`); (c) the common case `--root "/home/me/My Tree"` becomes `--root /home/me/My` plus a stray `Tree`, which the target's clap rejects — while the *identical* local command works, because `deploy::run_as` uses argv and no shell. The doc comment two lines above says the paths are "carried **verbatim**" and ADR-0078:71-77 (D3) builds a decision on that verbatim-ness; the code only achieves it for paths that survive a shell. Citation: ADR-0078 D3 ("`--config` and `--root` travel and reprint **verbatim**"), the `Plan` doc at `remote.rs:455-462`, and the repo's own one-rule-per-input discipline — D7 (`remote.rs:263-296`) exists solely because `--ssh` becomes an ssh argument, and the neighbouring `$HOME` token in the copy string (`remote.rs:160`) and run child (`remote.rs:252`) is unquoted for the same reason. Smallest fix: one `fn sh_quote(&str) -> String` beside `host_problem`, applied where `Plan::arguments` emits the two values (and to `$HOME` as `"$HOME"/.cache/…`); note in the doc comment that quoting also stops `~` from expanding. `ssh_resume` (`commands/deploy.rs:248-252`) has the same defect in the line an operator copy-pastes, so it moves with the same fix.

**2. P2/minor — `Machine::parse` accepts five words; ADR-0078, the ADR index and the unit test all say four.**
`remote.rs:309-315` accepts `x86_64`, `amd64`, **`x86-64`**, `aarch64`, `arm64`. ADR-0078:67 says "mapped through the four words a Linux answers (`x86_64`/`amd64`, `aarch64`/`arm64`)", `docs/stories/README.md:201` repeats "through four words", and the test is named `the_uname_words_this_build_may_hear_are_four_and_nothing_else` (`remote.rs:617`) while asserting `x86-64` is accepted (`remote.rs:618`). Either the word or the number is wrong; `x86-64` is not a `uname -m` answer on any Linux this spec targets. Smallest fix: drop the `"x86-64"` arm (and its test case) *or* change the three sentences to five. Citation: the house rule that a sentence may not claim more than was measured, and `docs/notes.md:460-461` ("a measurement or a review finding, not a preference").

**3. P2/minor — the unit test whose name claims two measurements makes one, and its second assertion cannot fail.**
`remote.rs:709-725`, `the_captured_children_are_batched_and_the_run_child_is_not`: the "run child is not batched" half never builds the run child's argv — the comment concedes it ("The run child's argv is built in `run`") — and the body then asserts `assert!(tools.interactive)` on a struct literal the test itself just set to `true` (`remote.rs:724`). Only the `batch()` half measures anything. The claim *is* measured, but one file over (`tests/remote.rs:298-300`). Smallest fix: delete the `Tools`/`assert!(tools.interactive)` tail, rename the test `the_captured_children_are_batched`, and let `tests/remote.rs` own the other half. Citation: `docs/notes.md:520-524` ("A test's claim can be half-strength and still green") and the brief's house style ("a test that cannot fail is worse than no test").

**4. P2/minor — `the_path_the_copy_lands_in_is_a_home_relative_shell_token` cannot fail on the code it names.**
`crates/holosmith/tests/remote.rs:551-573` never calls `Binary::remote_path`; it re-forms the expected name with `format!("{}/deploy-{}", remote::COPY_DIR, …)` (lines 556-559) and compares it to a hard-coded literal. Change `remote.rs:379-387` to `/tmp/deploy-…` and this test stays green; only the unit test at `remote.rs:648` (which does call the function) would catch it. It also duplicates that unit test and ends with a dead binding `let _: &Path = &path;` (line 572). Smallest fix: assert against `binary.remote_path()`'s tuple (the method is private, so expose it `pub(crate)` + a unit test, or drop this test as the duplicate it is). Citation: `docs/notes.md:520-524`; brief's "two implementations of one rule is the recurring defect class".

**5. P2/minor — a *failed remote run* is measured nowhere, and no arm tells stdout from stderr.**
ADR-0078:104-110 (D6) records three behaviours: the child's exit code becomes this command's, one local line says so, and **two** resume lines appear (the target's and the local one). Nothing measures any of them: every gate arm merges the streams (`>"$WORK/$name.….out" 2>&1`, e.g. `verify.sh:10966`), and the arms only exercise *pre-run* refusals; `tests/remote.rs:469-482` measures `Remote::run`'s status but never `commands::deploy::run_over_ssh`, so `commands/deploy.rs:204-221` (the `exited N` line, the `u8::try_from` mapping, the second resume line) is untested. `refused`'s documented split ("the sentence on stderr, and the command to re-run as the last line on stdout", `commands/deploy.rs:224-231`) is likewise asserted only. Smallest fix, no new shim needed: one gate arm running `--ssh me@box --config /nonexistent.toml` with `>out 2>err` — the local side never loads the config, so the target's binary exits 1, and the arm asserts exit 1, one `deploy: ssh:` line naming `exited 1`, the local resume on **stdout**, the refusal on **stderr**, and that the target's own `deploy: resume:` also arrived. Citation: `docs/notes.md:520-524`; brief's "does each test measure what its name says".

**6. P2/minor — "three ports" where the case asks the kernel for two.**
`docs/build.md:572` and the case's own header (`scripts/verify.sh:10909`) both say `python3` is needed for "three ports"; `case_deploy_ssh` calls `free_port` exactly twice (`verify.sh:10926-10927`) — control and preview — and the `_ping` socket is a unix socket, listed separately in the same sentence. Smallest fix: "two ports". Citation: brief's standards axis, "whether `docs/build.md`'s paragraph says anything false"; `docs/build.md` is a docs deliverable.

## Observations (report-only)

- **`ADR-0078:93` calls the third pre-run line a "fact it measured", but it is a plan.** `Sent::command_line` (`remote.rs:440-448`) prints "the target runs: …" *before* `remote.run` is spawned (`commands/deploy.rs:202-203`); if ssh cannot start, the earlier line already asserted what the target runs. The dry-run role line has an explicit `would be` shape for exactly this reason (`commands/deploy.rs:135-147`). Two-site fix if wanted: `"the target will run:"` + the needle at `verify.sh:10983`.
- **`-t` is keyed on stdout as well as stdin (`remote.rs:106`), so `holosmith server deploy --ssh me@box | tee log` on a terminal loses the pty that `sudo` needs** — the documented reason for `-t` at all (ADR-0078 D1, `remote.rs:41-49`). D1 records the readability gain of withholding it on a piped run but not this cost, and the CLI help promises "runs the same deploy there with sudo" (`cli.rs:140-142`) including for a no-`--root` run. Cheapest: one sentence in D1/`docs/notes.md`; better if cheap: `interactive = stdin.is_terminal()`.
- **`ADR-0078:143` lists the hub arm's applied steps as "2/5/6"**; the case measures 2, 5, 6 **and 7** (`verify.sh:11060-11075`) and `docs/build.md:578-579` says so. One-word fix.
- `status.code().unwrap_or(-1)` prints `exited -1` for a signalled child (`commands/deploy.rs:208-212`) — an exit code that does not exist, in a report that prides itself on that rule.
